## 1. Назначение и границы

Изолированный пилот проверяет HTML-кандидат финансового отчёта браузером и возвращает событие в ChatGPT Work через Outlook → Gmail. Он не изменяет Google Sheets, Apps Script, рабочие папки Reports/ или production-сценарии Nodul. Данные и артефакты пилота находятся в отдельной приватной папке Drive; ID этой папки, адреса и финансовые значения не публикуются в репозитории.

Это **не официальный runtime-контракт v1.0** и не замена проверкам агента отчёта. В производственную цепочку Claude → Nodul Telegram Sender → Telegram никаких изменений не внесено.

## 2. Поток и ответственность

1. Узел 17 настроен на **Only Created (new_file)** для файлов запроса нужного шаблона имени в авторизованной пилотной папке. Изменение уже существующего файла не создаёт новое событие. 23.11.2026 одиночный ручной запуск узла 17 прочитал заявку a02 и вернул Drive-событие; автоматическая обработка после Active не подтвердилась.
2. N00/N01 считывают запрос и выполняют строгую валидацию схемы, идентификаторов, попытки, SHA256 и `numeric_check`.
3. N02 проверяет наличие файла результата и квитанции: `VALIDATE`, `RESEND` либо `SKIP`. Несогласованное состояние останавливает обработку.
4. N03 загружает HTML по ID из запроса, подтверждает папку, размер, SHA256, UTF-8 и отсутствие активного/внешнего содержимого.
5. N04 запускает Headless Browser / Puppeteer на ширинах 320, 375, 390, 430, 768 px, измеряя переполнение и базовую структуру HTML.
6. N05 записывает результат: `PASS_GEOMETRY → VALIDATED`; `FAIL_GEOMETRY → REPAIR` до последней попытки и `EXCEPTION` на последней.
7. Nodul сохраняет результат в пилотной папке, отправляет сигнал через Outlook, затем сохраняет квитанцию для защиты от повторной отправки.
8. ChatGPT Work читает полный файл результата, а не финансовые данные из письма; при `REPAIR` создаёт следующий кандидат, при `VALIDATED` — тестовый финал.

## 5. Решение L2: PNG вне обязательного Nodul

Для пилота и следующей итерации Nodul проверяет **геометрию и базовую DOM-структуру**, а не качество визуальной композиции или смысловую корректность отчёта. PNG-снимки и ручная визуальная оценка — отдельная необязательная QA-процедура **вне основного сценария Nodul**. Возвращать `capture_screenshot=true` и добавлять Base64/PNG-ветку без отдельного решения не следует. Проверки чисел по данным Google Sheets сохраняются независимо от Nodul.

Это упрощение пилотной процедуры без изменений официальных контрактов и production-архитектуры; восстановление ошибочных связей после t10 — исправление реализации (L1).

**Внешний JSON-экспорт Nodul получен и структурно проверен 22.11.2026:** формат корректен, 20 функциональных узлов + 2 стикера, 21 связь, висячих рёбер и зависимостей от узлов t10 нет. Экспорт: 223 731 байт, SHA256 `cc7e48dac94800c2a931a0bdd6b13a00165ced1a03a5c70f74d78d904e0d100f`; версия экспортированного сценария `240`, Dev actualVersion `239`, внутренний checkpoint `237` (разные виды идентификаторов). Файл **хранится приватно и не публикуется в GitHub**, так как содержит служебные идентификаторы подключений/папки. Восстановление импортом и переподключение авторизаций **не проверялись**. Внутренний checkpoint остаётся дополнительным способом отката.

Перед повторной активацией после результата от 23.11.2026 необходимо:
1. Сохранить внешнюю JSON-копию в приватном защищённом хранилище, сверить SHA256; сохранить внутренний checkpoint Nodul как дополнительную точку отката. Если до активации будет проверяться импорт, делать это **в отдельный неактивный сценарий**, не поверх пилота; проверить необходимость переподключения авторизаций.
2. Проверить, что триггер ограничен только созданием пилотных запросов из нужной папки и что почтовый сигнал адресован тестовому получателю; не публиковать служебные ID и адреса.
3. Подтвердить отсутствие временных узлов, `capture_screenshot=false`, правильные входы N03/N04, а также наличие блокировки дублей.
4. Подготовить **отдельный новый** запрос и провести ограниченный тест с контролем результата, квитанции, события Work и отсутствия влияния на production. Повтор уже обработанного запроса должен давать `SKIP`.
5. Для этого ограниченного теста явное разрешение пользователя на одну активацию было получено 23.11.2026 и использовано; следующая активация или тестовое письмо требуют отдельного решения после установления причины сбоя.

При ошибке: остановить/деактивировать пилотный сценарий, сохранить диагностику без секретов и финансовых значений, восстановить внутреннюю резервную копию/контрольную точку, повторно проверить граф и только после этого возобновлять ручные тесты.

Повторное использование результата одиночного триггера не запускало цепочку автоматически.

Итог: конфигурация узла 17, ручное чтение события и загрузка/чтение a02 подтверждены. Автоматическое срабатывание Prod не подтверждено; ручная обработка остановилась на узле 3. Заявка a02 использует `report_id=999905`, имя с `run_id`, поле `qa_folder_id` и не содержит `pilot_id`; после исправления версии она всё равно не пройдёт остальные проверки. Попытка привести её к Report 10 контракту потребовала бы ещё указать `analysis_checked≥1`, но в a02 сейчас `analysis_checked=0`. В синтетической папке найден `report_data_999904.json`, тогда как кандидат a02 — HTML для 999905; это не согласованный источник числовой сверки. Поэтому заявку не редактировали и повторно не запускали. Протокол v0.1 помечен `Proposed — только спецификация, не действующий runtime-контракт`: обнаружено несовпадение универсального предложенного контракта с Report 10-specific пилотом, а не подтверждён дефект данных. Создание result/receipt, Outlook-send и обработка Work не выполнялись. Gmail содержит только более ранние события для report_id 999902–999904, не новое письмо для 999905.

Текущее состояние: **Active выключен**, **Prod v245 остаётся опубликованным**, Development не активен. После проверок новых файлов/заявок/писем не создавали. Причина, по которой автоматическая подписка не запустилась, остаётся не установленной. Перед следующим продакшен-переключением/созданием нового события нужно отдельно подтвердить это действие и выбрать следующий тестовый шаг.
