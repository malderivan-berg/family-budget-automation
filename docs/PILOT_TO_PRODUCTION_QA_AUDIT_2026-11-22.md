## 1. Сопоставление текущих контуров

**Production v1.0:** Google Sheets → Apps Script (`report_data_N.json`, /fire) → агент Claude (`analysis_N.json`, `report_N.html`, `check_numbers.py`, `render_check.py`) → `telegram_request_N.json` → Nodul сценарий 2 → Telegram → `telegram_response_N.json` → Apps Script проверка доставки через 30 минут.

**Изолированный пилот:** Drive request → Nodul SHA256 + Puppeteer → result JSON → Outlook → Gmail → ChatGPT Work → исправление / финальный тестовый HTML. Не связан с агентом Claude или рабочим Telegram Sender; целенаправленно содержит жёсткие ограничения по отчёту №10.

## 3. Подтверждённые технические несовместимости пилота

Экспорт Nodul содержит привязки к `report_id=10`, `pilot_id=FBA_R10_WORK_NODUL_PILOT`, конкретному Drive folder ID, именам `fba_layout_request_r10_a01–a04.json`, фиксированным попыткам 1–4, ограниченному получателю, теме `FBA_REPORT10_DRYRUN`. Их перенос требует параметризации N01, N05, N06, Drive-фильтров и модели событий.

Claude `agent/report_agent.md` v2.1 получает через API-триггер **четыре** поля, пишет в папку отчёта и `Telegram/Outbox`; он не обслуживает пилотные события из Outlook/Gmail. В production существующий `telegram_request_N.json` запускает доставку **сразу после проверки и загрузки HTML**. Для ожидания ответа внешнего валидатора пришлось бы менять порядок сигналов/правила запуска, то есть разрабатывать новый контракт и пути восстановления. Такой проект не считать минимальным L2-изменением.

## 4. Дефект, который действительно нужно исправить

Текущий `agent/tools/render_check.py`:
- проверяет браузером только `390 px`;
- создаёт PNG для ручной проверки (это **не** Nodul PNG-ветка);
- возвращает `exit 0` при PASS, `exit 1` при OVERFLOW и `exit 3`, если Playwright не установлен;
- `agent/report_agent.md` v2.1 **разрешает продолжать публикацию при exit 3**.

Следовательно, сейчас мобильная проверка может быть пропущена, а значение `PASS` на 390 px не гарантирует отсутствия ошибки на 320 или 768 px.

Важно: наличие Python-модуля Playwright не доказывает, что в среде задачи Claude установлен браузер Chromium. Не переводить на fail-closed в production без проверки на реальном тестовом запуске.

## 5. Рекомендуемая последовательность реализации (без изменения контрактов)

**P0 — подтвердить окружение в тестовом запуске Claude (L1, read-only).**

В тестовом режиме на локальном/тестовом HTML проверить запуск `render_check.py` именно из среды задачи Claude: версия Python/Playwright, доступность Chromium, реальный exit code; не публиковать Telegram Request. Если Playwright отсутствует — сначала выбрать и испытать надёжный способ установки/доступности в данной среде, не меняя production-инструкцию. Не считать тест локального компьютера подтверждением среды Claude.

**P1 — минимальное усиление `render_check.py` (L2).**

Один модуль. Пройти пять фиксированных ширин; проверить на каждой `scrollWidth <= viewport` и реальные переполнения видимых элементов; исключить ложноположительные результаты на скрытых/декоративных элементах; вернуть краткий машиночитаемый JSON и ненулевой exit при ошибках. Сохранить обратную совместимость CLI `--html`, `--png`, `--width` для текущего вызова агента. PNG 390 px для ручной оценки в Claude не отменять автоматически. HTML не менять и числа не пересчитывать. Тесты должны включать корректный HTML v03 (PASS), испорченный HTML с overflow (FAIL), пустой документ (FAIL), отсутствие браузера (явный `UNAVAILABLE`).

**P2 — инструкция агента, тестовый режим (L2).**

Только после P0/P1: скорректировать шаг 8 `agent/report_agent.md`, установить обязательную пятиширинную проверку; при `FAIL/UNAVAILABLE` — **не создавать** `telegram_request_N.json`, сформировать `report_N_error.md` и использовать существующий GAS alert. Не менять порядок создания HTML, Telegram Request/Response, Report Data или доступ к Sheets. Проверить отдельно идемпотентность шага 1 (если HTML уже существует, текущая инструкция умеет досоздать запрос без повторной проверки): **перед повторной отправкой QA должна быть проверена либо подтверждена**. Не включать fail-closed в рабочий агент до теста среды и сценария повторной доставки.

**P3 — приёмка и включение (L2).**

На тестовом отчёте: полный PASS на пяти ширинах → сверка чисел → обратный SHA256 после Drive → публикация тестового Telegram Request → успешный `telegram_response`; отдельно намеренный overflow / отсутствие браузера не должны приводить к отправке. Проверить, что `resendLastReport_` не обходится без достаточной проверки уже опубликованного HTML; если необходим отдельный revalidation gate, оформить до rollout. Получить явное согласие на изменение рабочей инструкции Claude/production.

## 6. Если независимый валидатор Nodul принципиально нужен

Альтернативный дизайн: независимую геометрическую проверку выполнять **внутри отдельной копии Telegram Sender** после скачивания HTML и **до** `sendDocument`, без Outlook/Gmail/Work и без переиспользования пилотного протокола `a01–a04`. Fail → не отправлять, записать допустимый отрицательный статус в `telegram_response_N.json`, чтобы GAS предупредил пользователя. Это потенциально L2, только если официальные контракты и допустимые статусы сохраняются; изменение Telegram Request/Response или условий запуска — L3, требует отдельного согласования. **Сценарий 2 Nodul не экспортирован для этого аудита**, поэтому реальная совместимость и объём правок пока не доказаны.

Этот вариант даёт независимость проверки от Claude, но меняет действующий Telegram Sender. Выбирать его после оценки P0/P1 и получения фактического экспорта рабочего сценария 2, а не на основе предположений.

## 7. Решение и границы

- **Принято к предложению:** сначала P0 (read-only диагностика доступности браузера Claude). Затем P1/P2 только в тестовом режиме, с тестами и откатом.
- **Не делалось:** правки GAS, Nodul, Claude-инструкции, финансовых данных, production Deploy/Active, Telegram/Outbox.
- **Запрещено без отдельного решения:** включать в production пилот Nodul как постоянный валидатор; менять официальные контракты; отключать существующие проверки чисел и SHA256; переключать `TEST_MODE`; делать обязательную проверку, которую реальное окружение не умеет выполнять.
- **Откат будущего P1/P2:** восстановить предыдущую версию только `agent/tools/render_check.py` и `agent/report_agent.md` из Git; никаких изменений GAS/Nodul при выбранном маршруте не требуется.
