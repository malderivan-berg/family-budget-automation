## Контракт для одного тестового запуска

1. Рассмотреть предварительное резервирование report_id в изолированной Sheets и создание GAS выгрузки при подготовке стенда. Сохранить UUID один раз. Для сохранения строгого allowlist Work использовать заранее зарезервированный Drive ID манифеста, если доступный Drive-интерфейс позволяет создать файл с таким ID. Иначе требуется отдельный доверенный контекст подготовки с привязкой к фактической выгрузке и проверяемым START. Газовый маршрут не должен вызывать Claude. После первоначального запуска GAS создаёт START последним, без ручной записи или письма.
2. QA получает фактические Drive metadata и читает по найденным ID; полный листинг, точное имя, непосредственный родитель, MIME и состояние файла. Отсутствие совпадения после полного поиска передаётся пустым массивом; неоднозначность останавливает граф. QA-result, receipt и письмо связываются с фактическим request_file_id, UUID, request_id и SHA-256. При неопределённой доставке — QA_DELIVERY_UNCERTAIN.
3. Одиночный Run once QA может закончиться на HTML до появления JSON (гипотеза в PR №12). Требуется автоматическое наблюдение именно за новой заявкой и фактическая история исполнения пяти ширин. QA должна записать результат до Outlook; Work повторно читает исходный анализ, BUILD evidence и кандидат и выполняет обе числовые проверки.
4. Telegram Request остаётся v1.1, один разрешённый получатель и отдельный Outbox. Создать Request после побайтового readback финала. Response v1.0 связывать по requestId из Request и reportId из проверенного Request и имени Response: в JSON Response отдельного reportId нет. Дополнительно сверять фактического ожидаемого пользователя, успешный messageId и сводку 1/1/0; отклонять дубли, устаревшие файлы и неоднозначность. В тестовом GAS разделить ожидание появления Request и отсчёт срока Telegram-доставки с момента проверенного Request. При неопределённости повторно не отправлять.
5. Публиковать в GitHub агрегированные результаты и статусы без приватных Drive ID, контактов и финансовых данных. Перед любой активацией зафиксировать начальные версии тестовых сценариев и отключение тестовых триггеров как точку отката. Источники №19 и №20 подтверждают отдельные переходы для старых запусков; переносить их результаты на новый UUID нельзя.
