## 1. Назначение документа

Настоящий документ определяет официальный внутренний контракт между модулем `ReportBuilder.gs` (Apps Script) и модулем `HtmlReportRenderer.gs` (Renderer).

**Report Model** является единственным источником данных для Renderer. Renderer не обращается к Google Sheets, LLM или любым другим источникам.

Данная спецификация определяет:
1. структуру Report Model;
2. типы компонентов и их данные;
3. правила формирования модели;
4. принципы расширения;
5. требования к совместимости между версиями;
6. правила взаимодействия между ReportBuilder и Renderer.

Спецификация не зависит от конкретной LLM, конкретного Renderer и не содержит требований к визуализации.

---

## 2. Область применения

Report Model используется всеми компонентами проекта, участвующими в формировании аналитического отчёта.

Типовая цепочка обработки данных:

```
Google Sheets
        │
        ▼
Export.gs
        │
        ▼
AI Job Package
        │
        ▼
LLM (только текст)
        │
        ▼
LLM Analysis (минимальный JSON)
        │
        ▼
ReportBuilder.gs
        │
        ▼
Report Model  ◄── НАСТОЯЩИЙ КОНТРАКТ
        │
        ▼
Renderer
        │
        ▼
HTML Report (пользовательский артефакт)
```

В дальнейшем допускается использование Report Model для различных пользовательских интерфейсов:
1. HTML Report;
2. PDF;
3. Web Dashboard;
4. Mobile Application;
5. будущие интерфейсы проекта.

Таким образом, Report Model является независимым контрактом обмена данными и не зависит от конкретного пользовательского интерфейса.

## 3. Основные принципы

### 3.1. Единый источник данных для Renderer

Renderer получает только одну объектную модель отчёта (Report Model) и не обращается к другим источникам данных.

Все данные для отчёта объединяются в единую модель до передачи в Renderer.

### 3.2. Разделение бизнес-смысла и представления

ReportBuilder не вычисляет бизнес-показатели (капитал, доходность, проценты, финансовые KPI).

ReportBuilder может выполнять подготовку данных для представления:
- форматирование дат и валют;
- сортировка;
- подготовка массивов для визуализации;
- вычисление координат SVG;
- нормализация структур данных.

### 3.3. LLM только анализирует

LLM генерирует только текстовую аналитику (Executive Summary, Insights, Recommendations, Warnings, Conclusion).

LLM не генерирует:
- HTML;
- JSON-схему отчёта;
- числовые KPI;
- визуализации;
- исторические ряды.

### 3.4. Компонентная независимость

Каждый компонент отчёта является полностью самостоятельным.

Компонент не должен зависеть от существования других компонентов.

Это позволяет:
1. менять порядок компонентов;
2. исключать отдельные компоненты;
3. добавлять новые компоненты;
4. использовать компоненты в других интерфейсах.

### 3.5. Renderer остаётся универсальным

Report Model не делает Renderer зависимым от конкретного типа компонентов.

Renderer получает описание компонента и самостоятельно выбирает механизм отображения.

Это позволяет без изменения архитектуры проекта добавлять новые типы компонентов в будущих версиях.

### 3.6. Расширяемость

При развитии проекта допускается добавление новых типов компонентов.

Новые типы не должны нарушать работу существующих компонентов.

Поддерживается принцип:
> Новые версии расширяют существующую модель, но не изменяют её фундаментальную структуру.

### 3.7. Полная обратная совместимость

Любой Report Model, соответствующий версии 1.0, считается корректным документом версии 1.0.

Все новые типы компонентов являются необязательными.

Renderer обязан корректно работать как при наличии новых типов, так и при их отсутствии.

---

## 4. Общая структура Report Model

Report Model состоит из двух частей:
1. **Метаданные** — служебная информация об отчёте.
2. **Компоненты** — массив независимых блоков отчёта.

Высокоуровневая структура:

```json
{
  "metadata": { ... },
  "components": [ ... ]
}
```

Не все компоненты являются обязательными.

Каждый Renderer должен корректно работать при отсутствии необязательных компонентов.

---

## 5. Метаданные отчёта

Объект `metadata` содержит служебную информацию о сформированном отчёте.

Метаданные не являются частью финансового анализа и используются исключительно для идентификации документа.

Пример состава объекта:

```json
{
  "metadata": {
    "reportId": "123",
    "modelVersion": "1.0",
    "reportPeriod": "2026-07",
    "generationDate": "2026-07-21",
    "currency": "RUB",
    "language": "ru"
  }
}
```

Назначение отдельных полей:

| Поле | Назначение |
|------|------------|
| `reportId` | Уникальный идентификатор отчёта |
| `modelVersion` | Версия Report Model Specification |
| `reportPeriod` | Анализируемый период |
| `generationDate` | Дата формирования отчёта |
| `currency` | Основная валюта отчёта |
| `language` | Локализация документа |

Допускается расширение данного объекта без нарушения совместимости.

---

## 6. Компоненты отчёта

Каждый компонент представляет собой независимый блок отчёта.

Типичная структура компонента:

```json
{
  "type": "...",
  "order": 1,
  "data": { ... }
}
```

Назначение полей:

| Поле | Тип | Обязательность | Назначение |
|------|-----|----------------|------------|
| `type` | string | ✅ | Тип компонента (определяет обработчик в Renderer) |
| `order` | integer | ✅ | Порядок отображения (меньше = раньше) |
| `data` | object | ✅ | Данные компонента (структура зависит от типа) |

---

## 7. Типы компонентов (полный набор версии 1.0)

Версия 1.0 определяет **12 типов компонентов**:

### 7.1. `report_metadata`

Назначение: отображение параметров отчётного периода (даты, длительность, ставка, доли капитала).

Структура `data`:

```json
{
  "periodStart": "2026-07-03",
  "periodEnd": "2026-07-10",
  "durationDays": 7,
  "interestRate": 11.0,
  "currency": "RUB",
  "husbandShare": 61.6,
  "wifeShare": 35.5
}
```

Источник данных: Google Sheets (через ReportBuilder).

### 7.2. `kpi_dashboard`

Назначение: отображение ключевых показателей (Net Worth, Liquid Assets, Weekly Change и т.д.).

Структура `data`:

```json
{
  "metrics": [
    {
      "label": "Чистый капитал",
      "value": 15000000,
      "unit": "RUB",
      "change": 250000,
      "changePercent": 1.7,
      "direction": "up"
    }
  ]
}
```

Источник данных: Google Sheets (через ReportBuilder).

### 7.3. `insight_list`

Назначение: отображение аналитических выводов.

Структура `data`:

```json
{
  "title": "Ключевые выводы",
  "items": [
    {
      "text": "Рост капитала ускоряется третью неделю подряд.",
      "category": "positive"
    }
  ]
}
```

Источник данных: LLM (через LLM Analysis).

### 7.4. `recommendation_list`

Назначение: отображение рекомендаций.

Структура `data`:

```json
{
  "items": [
    {
      "text": "Рассмотреть размещение бездействующих средств.",
      "priority": "high"
    }
  ]
}
```

Источник данных: LLM (через LLM Analysis).

### 7.5. `watch_item`

Назначение: отображение детального блока с показателем, требующим внимания (необъяснённое изменение, бездействующие деньги, упущенный доход и т.д.).

Структура `data`:

```json
{
  "title": "Необъяснённое изменение капитала семьи",
  "currentValue": -135399,
  "previousValue": 1438295,
  "change": -1573694,
  "unit": "RUB",
  "severity": "critical",
  "context": "Необъясненное изменение — это «разрыв» между фактическим изменением капитала и суммой всех идентифицированных причин...",
  "details": [
    { "label": "Жена", "value": -74987 },
    { "label": "Муж", "value": -39707 }
  ]
}
```

Поле `severity` принимает значения:
- `critical` — критический приоритет;
- `high` — высокий приоритет;
- `medium` — средний приоритет;
- `low` — низкий приоритет.

Источник данных: Google Sheets (числовые значения) + LLM (текстовый контекст).

### 7.6. `history_chart`

Назначение: отображение исторических данных (SVG-график).

Структура `data`:

```json
{
  "title": "Динамика капитала",
  "chartType": "sparkline",
  "series": [
    { "date": "2026-05-12", "value": 14200000 },
    { "date": "2026-05-19", "value": 14450000 }
  ]
}
```

Источник данных: Google Sheets (через ReportBuilder, чтение из архива).

### 7.7. `text_block`

Назначение: отображение произвольного текстового блока (заключение, комментарий, общая оценка).

Структура `data`:

```json
{
  "title": "Заключение",
  "text": "Финансовое состояние семьи стабильно."
}
```

Источник данных: LLM (через LLM Analysis).

### 7.8. `comparison_table`

Назначение: сравнение двух или нескольких величин.

Структура `data`:

```json
{
  "title": "Сравнение периодов",
  "items": [
    { "label": "Текущая неделя", "value": 15000000 },
    { "label": "Предыдущая неделя", "value": 14750000 }
  ]
}
```

Источник данных: Google Sheets (через ReportBuilder).

### 7.9. `capital_structure`

Назначение: отображение структуры капитала (распределение по классам активов).

Структура `data`:

```json
{
  "title": "Структура капитала",
  "items": [
    { "label": "Недвижимость", "value": 8000000, "share": 53.3 },
    { "label": "Инвестиции", "value": 4000000, "share": 26.7 }
  ],
  "total": 15000000
}
```

Источник данных: Google Sheets (через ReportBuilder).

### 7.10. `change_breakdown`

Назначение: декомпозиция изменения капитала (waterfall-подобная визуализация вклада каждого фактора).

Структура `data`:

```json
{
  "title": "Декомпозиция изменения капитала",
  "total": -162498,
  "unit": "RUB",
  "items": [
    { "label": "Доходы от плановых операций", "value": 204248, "direction": "positive" },
    { "label": "Расходы по плановым операциям", "value": -237235, "direction": "negative" },
    { "label": "Переоценка инвестиций", "value": -5022, "direction": "negative" },
    { "label": "Погашение ипотеки", "value": 6729, "direction": "positive" },
    { "label": "Необъяснённое изменение", "value": -124489, "direction": "negative" }
  ]
}
```

Источник данных: Google Sheets (через ReportBuilder).

### 7.11. `budget_variance`

Назначение: сравнение плановых и фактических значений (бюджетное отклонение).

Структура `data`:

```json
{
  "title": "Плановые доходы и расходы",
  "items": [
    {
      "label": "Доходы семьи",
      "planned": 191306,
      "actual": 178712,
      "variance": -12594,
      "variancePercent": -6.2,
      "unit": "RUB"
    },
    {
      "label": "Расходы семьи",
      "planned": -121146,
      "actual": -339194,
      "variance": -218048,
      "variancePercent": 180.0,
      "unit": "RUB"
    }
  ]
}
```

Источник данных: Google Sheets (через ReportBuilder).

### 7.12. `section`

Назначение: контейнер секции с заголовком и вложенными компонентами (например, "Анализ капитала мужа", "Анализ капитала жены").

Структура `data`:

```json
{
  "title": "Анализ капитала мужа",
  "components": [
    { "type": "kpi_dashboard", "data": { ... } },
    { "type": "capital_structure", "data": { ... } },
    { "type": "comparison_table", "data": { ... } },
    { "type": "insight_list", "data": { ... } }
  ]
}
```

**Правила обработки вложенных компонентов:**
1. Вложенные компоненты не имеют собственного поля `order` — порядок определяется порядком в массиве `components`.
2. Вложенные компоненты обрабатываются Renderer рекурсивно.
3. Допускается произвольная глубина вложенности (рекомендуется не более 2 уровней).
4. Вложенные компоненты могут быть любого типа, включая `section` (рекурсивно).

Источник данных: Google Sheets + LLM (комбинация).

## 9. Правила обработки компонентов

### 9.1. Порядок компонентов

Renderer сортирует компоненты по полю `order` (возрастание).

Компоненты с одинаковым `order` отображаются в порядке поступления.

### 9.2. Отсутствие компонента

Если компонент отсутствует в массиве — Renderer пропускает его.

Отсутствие компонента не считается ошибкой.

### 9.3. Неизвестный тип компонента

Если Renderer встречает неизвестный `type`, он использует fallback-представление:

```html
<section class="component unknown">
  <div class="warning">Неизвестный тип компонента: {type}</div>
  <pre>{JSON.stringify(data, null, 2)}</pre>
</section>
```

Это обеспечивает отказоустойчивость при появлении новых типов в будущих версиях.

### 9.4. Пустые данные

Если `data` компонента пустое или не содержит значимой информации — Renderer может пропустить компонент без отображения.

### 9.5. Рекурсивная обработка `section`

Если компонент типа `section` содержит вложенные компоненты, Renderer обрабатывает их рекурсивно:

1. Рендерит заголовок секции.
2. Для каждого вложенного компонента вызывает соответствующий обработчик.
3. Оборачивает результат в контейнер секции.

## 10. Принципы расширения модели

### 10.1. Добавление новых типов компонентов

Допускается добавление новых типов компонентов.

Новые типы не должны изменять структуру существующих типов.

Каждый новый тип должен иметь:
1. уникальное имя `type`;
2. чётко определённую структуру `data`;
3. описание источника данных.

### 10.2. Добавление новых полей в компоненты

Допускается добавление новых необязательных полей в `data` существующих компонентов.

Не допускается:
1. изменение смысла существующих полей;
2. изменение типа существующих полей;
3. изменение обязательности существующих полей.

### 10.3. Удаление типов компонентов

Удаление типов компонентов допускается только при выпуске новой мажорной версии спецификации.

Версии семейства 1.x не должны удалять существующие типы.

## 11. Требования к разработчикам ReportBuilder

ReportBuilder обязан:
1. читать финансовые данные из Google Sheets (не вычислять);
2. читать исторические данные из архива;
3. читать текстовую аналитику из LLM Analysis;
4. валидировать полноту данных;
5. формировать единый Report Model;
6. соблюдать порядок компонентов (поле `order`);
7. корректно формировать вложенные компоненты в `section`.

ReportBuilder не должен:
1. выполнять финансовые расчёты;
2. изменять аналитические выводы LLM;
3. генерировать HTML или визуализации;
4. обращаться к Renderer или другим компонентам.

---

## 12. Требования к разработчикам Renderer

Renderer обязан:
1. корректно обработать все 12 известных типов компонентов;
2. безопасно игнорировать неизвестные типы (fallback);
3. сортировать компоненты по полю `order`;
4. обеспечивать корректное отображение всех данных;
5. сохранить работоспособность при отсутствии необязательных компонентов;
6. рекурсивно обрабатывать вложенные компоненты в `section`.

Renderer не должен:
1. выполнять финансовые расчёты;
2. изменять аналитические выводы;
3. обращаться к Google Sheets, LLM или другим источникам;
4. генерировать новые аналитические данные.

---

## 13. Совместимость с AI Report Schema v1.2

AI Report Schema v1.2 является legacy-спецификацией и не является
входным контрактом Renderer целевой архитектуры v1.0.

Renderer v1.0 принимает только Report Model v1.0.

Если при миграции потребуется обработка существующего AI Report Schema,
совместимость реализуется отдельным временным адаптером:

AI Report Schema v1.2
→ Legacy Adapter
→ Report Model v1.0
→ Renderer

Поддержка legacy-адаптера не является частью Report Model Contract
и может быть удалена после завершения миграции.

## 15. Рекомендации по развитию спецификации

Следующие направления развития рассматриваются как приоритетные для будущих версий:

1. новые типы компонентов (макроэкономический обзор, депозиты, календарь, анализ недвижимости);
2. расширение поддержки исторических данных (множественные ряды в `history_chart`);
3. развитие объектов визуализации (donut chart, stacked bar, gauge);
4. поддержка интерактивных пользовательских интерфейсов;
5. дополнительные аналитические сущности Family Office;
6. развитие поддержки долгосрочного финансового планирования.

При этом фундаментальная архитектура Report Model (метаданные + массив компонентов) должна оставаться неизменной.

---

## 16. Заключение

Report Model является центральным внутренним контрактом между ReportBuilder и Renderer.

Настоящая спецификация обеспечивает:
1. разделение ответственности между компонентами;
2. независимость Renderer от конкретных источников данных;
3. возможность появления новых пользовательских интерфейсов без изменения логики ReportBuilder;
4. масштабируемость проекта;
5. долгосрочную устойчивость архитектуры.

Report Model становится не просто форматом обмена JSON-документами, а одним из фундаментальных архитектурных компонентов Family Budget Automation, определяющим взаимодействие между подготовкой данных и пользовательским опытом.
