**AI Report Schema Specification v1.2**

**Version: 1.2**

**Status: Legacy / Superseded Design — Not**

**Current Project: Family Budget Automation**

**Document Type: Historical Technical Specification**

**ARCHITECTURE STATUS**

Настоящий документ описывает предыдущую структурированную архитектуру аналитического отчета и сохраняется как историческая спецификация.

Документ не является контрактом текущей стабильной версии проекта v0.9. В v0.9 используется HTML-first pipeline, определенный Project Handbook v0.9. Документ также не является целевым контрактом архитектуры v1.0.

Целевая архитектура v1.0 использует:

AI Job Package

→ LLM Analysis

→ ReportBuilder

→ Report Model

→ Renderer

→ HTML Report

Функции, ранее объединенные в AI Report Schema, разделены между:

\- LLM Analysis Contract — аналитический смысл;

\- Report Model Specification — единая модель для Renderer.

AI Report Schema v1.2 сохраняется исключительно как legacy reference для истории проекта и возможной миграции существующего кода.

Все нормативные формулировки ниже, включая упоминания «официального», «единственного» и «центрального» контракта, сохраняются исключительно как часть исторического содержания спецификации v1.2 и не описывают текущее или целевое состояние проекта.

**1. Назначение документа**

Настоящий документ определяет официальный контракт обмена аналитическими данными между языковой моделью (LLM) и пользовательскими интерфейсами проекта Family Budget Automation.

AI Report Schema является единственным официальным форматом представления результатов анализа, выполняемого искусственным интеллектом.

Данная спецификация определяет:

- структуру выходных данных LLM;

- правила формирования аналитической информации;

- принципы расширения схемы;

- требования к совместимости между версиями;

- правила взаимодействия между AI и пользовательскими интерфейсами проекта.

Спецификация не зависит от конкретной модели искусственного интеллекта и не содержит требований к реализации отдельных программных модулей.

**2. Область применения**

AI Report Schema используется всеми компонентами проекта, участвующими в формировании аналитического отчета.

Типовая цепочка обработки данных выглядит следующим образом:

Google Sheets

│

▼

AI Job Package

│

▼

Large Language Model

│

▼

AI Report Schema

│

▼

Renderer

│

▼

HTML Report

В дальнейшем допускается использование одного и того же AI Report Schema для различных пользовательских интерфейсов, включая:

- HTML Report;

- Telegram;

- PDF;

- Web Dashboard;

- Mobile Application;

- будущие интерфейсы проекта.

Таким образом, AI Report Schema является независимым контрактом обмена аналитическими данными и не зависит от конкретного пользовательского интерфейса.

**3. Основные принципы**

Настоящая спецификация основана на следующих принципах.

**3.1. AI является аналитиком**

LLM выполняет исключительно аналитическую работу.

AI:

- анализирует финансовые показатели;

- выявляет закономерности;

- определяет риски;

- формирует выводы;

- готовит данные для последующей визуализации.

AI не занимается построением пользовательского интерфейса.

**3.2. Renderer является визуализатором**

Renderer отвечает исключительно за преобразование AI Report Schema в пользовательское представление.

Renderer:

- создает HTML;

- строит SVG;

- отображает диаграммы;

- оформляет карточки;

- использует дизайн-систему проекта.

Renderer не выполняет финансовых расчетов и не изменяет результаты анализа.

**3.3. Google Sheets остается единственным источником финансовых данных**

Все финансовые показатели рассчитываются исключительно в Google Sheets.

AI не пересчитывает показатели.

Renderer не пересчитывает показатели.

Все числовые значения, используемые в отчете, должны соответствовать данным, переданным в AI Job Package.

**3.4. Разделение ответственности**

Каждый компонент проекта отвечает только за собственную область ответственности.

| **Компонент**    | **Ответственность** |
|------------------|---------------------|
| Google Sheets    | Финансовые расчеты  |
| AI               | Анализ данных       |
| AI Report Schema | Контракт обмена     |
| Renderer         | Визуализация        |
| HTML Template    | Дизайн              |

Ни один компонент не должен выполнять функции другого.

**3.5. Независимость от интерфейса**

AI не должен знать:

- как будет выглядеть HTML;

- какие CSS используются;

- какие SVG строятся;

- каким образом реализованы карточки;

- каким Renderer будет пользоваться пользователь.

Вся информация передается исключительно в виде структурированных аналитических данных.

**3.6. Независимость от модели искусственного интеллекта**

Спецификация не зависит от конкретной LLM.

Допускается использование:

- OpenAI;

- Anthropic;

- Google;

- DeepSeek;

- Perplexity;

- локальных моделей;

- любых будущих моделей.

При смене модели AI структура AI Report Schema изменяться не должна.

**3.7. Расширяемость**

При развитии проекта допускается добавление новых разделов, объектов и аналитических сущностей.

Новые элементы не должны нарушать работу существующих Renderer.

Поддерживается принцип:

Новые версии расширяют существующую схему, но не изменяют ее фундаментальную структуру.

**4. Новые возможности версии 1.2**

Версия 1.2 является эволюционным развитием версии 1.1.

Все документы и программные компоненты, совместимые с версией 1.1, должны продолжать корректно работать после внедрения версии 1.2.

Главной целью версии 1.2 является подготовка проекта к развитию визуальной аналитики.

Для этого вводятся следующие архитектурные принципы.

**4.1. Разделение аналитики и визуализации**

Версия 1.1 описывала преимущественно аналитические данные.

Версия 1.2 вводит дополнительный уровень абстракции.

Теперь AI может передавать не только результаты анализа, но и рекомендации по способу их визуального представления.

При этом AI не описывает HTML, SVG или CSS.

AI описывает только аналитический объект и рекомендуемый способ его отображения.

Окончательное решение о визуальном представлении всегда принимает Renderer.

**4.2. Визуализация является частью аналитики**

Современный аналитический отчет состоит не только из текста.

Диаграммы, графики, индикаторы и карточки являются частью аналитического сообщения.

Поэтому AI может передавать структурированные данные, предназначенные для построения визуальных компонентов.

При этом сами визуальные компоненты продолжают строиться Renderer.

**4.3. Renderer остается универсальным**

Версия 1.2 не делает Renderer зависимым от конкретного типа диаграмм.

Напротив, вводится единый подход, при котором Renderer получает описание аналитического объекта и самостоятельно выбирает соответствующий механизм отображения.

Это позволяет без изменения архитектуры проекта добавлять новые типы визуальных компонентов в будущих версиях.

**4.4. Подготовка к исторической аналитике**

Версия 1.2 закладывает основу для поддержки:

- исторических данных;

- динамики показателей;

- сравнения периодов;

- временных рядов;

- накопительной статистики.

Поддержка данных возможностей является необязательной для версии 1.2, однако структура схемы должна предусматривать возможность их последующего внедрения без изменения существующих контрактов.

**4.5. Полная обратная совместимость**

Любой AI Report Schema, соответствующий версии 1.1, считается корректным документом версии 1.2.

Все новые сущности версии 1.2 являются необязательными.

Renderer обязан корректно работать как при наличии новых объектов, так и при их отсутствии.

**5. Общая структура AI Report Schema**

Версия 1.2 сохраняет объектную модель версии 1.1.

Каждый логический раздел отчета представляет собой самостоятельный объект.

Все объекты могут содержать как аналитические данные, так и дополнительные сведения, необходимые для их корректного отображения.

Высокоуровневая структура документа выглядит следующим образом:

metadata

summary

sections

visualizations

appendix

Не все разделы являются обязательными.

Каждый Renderer должен корректно работать при отсутствии необязательных разделов.

**6. Метаданные документа**

Объект **metadata** содержит служебную информацию о сформированном отчете.

Метаданные не являются частью финансового анализа и используются исключительно для идентификации документа.

Пример состава объекта:

metadata

reportId

schemaVersion

generatedAt

reportingPeriod

currency

locale

Назначение отдельных полей:

| **Поле**        | **Назначение**                  |
|-----------------|---------------------------------|
| reportId        | Уникальный идентификатор отчета |
| schemaVersion   | Версия AI Report Schema         |
| generatedAt     | Дата формирования AI-анализа    |
| reportingPeriod | Анализируемый период            |
| currency        | Основная валюта отчета          |
| locale          | Локализация документа           |

Допускается расширение данного объекта без нарушения совместимости.

**7. Принципы организации аналитических данных**

**7.1. Раздел является независимым**

Каждый раздел отчета должен быть полностью самостоятельным.

Раздел не должен зависеть от существования других разделов.

Это позволяет:

- менять порядок разделов;

- исключать отдельные разделы;

- добавлять новые разделы;

- использовать разделы в других интерфейсах.

**7.2. Раздел содержит только свою аналитику**

Раздел должен описывать только собственную предметную область.

Например:

Раздел "Инвестиции" не должен повторно анализировать семейный бюджет.

Раздел "Ликвидность" не должен содержать рекомендации по ипотеке.

Раздел "Риски" не должен повторять Executive Summary.

**7.3. Аналитика является структурированной**

Любая информация должна быть представлена максимально структурированно.

Предпочтительно:

riskLevel

вместо

"Риск высокий."

Предпочтительно:

change = -8.5

trend = down

вместо

"Показатель заметно снизился."

Текстовые комментарии используются только тогда, когда информация не может быть представлена структурированными данными.

**8. Универсальные аналитические объекты**

Версия 1.2 вводит понятие универсальных аналитических объектов.

Они предназначены для повторного использования различными разделами отчета.

Каждый Renderer должен поддерживать данные объекты независимо от конкретного раздела.

**8.1. Metric**

Metric является базовым аналитическим объектом проекта.

Он используется для представления любого измеримого показателя.

Типичный состав объекта:

label

value

previousValue

change

changePercent

trend

unit

Назначение:

- KPI;

- остатки;

- доходность;

- изменение капитала;

- показатели эффективности;

- любые количественные характеристики.

Metric является основным строительным блоком большинства отчетов.

**8.2. Insight**

Insight представляет собой отдельный аналитический вывод.

Insight не содержит рекомендаций.

Insight отвечает только на вопрос:

Что произошло?

Типичный состав:

title

summary

details

importance

**8.3. Recommendation**

Recommendation описывает рекомендуемое действие.

Recommendation отвечает на вопрос:

Что следует сделать?

Типичный состав:

title

action

priority

reason

expectedEffect

**8.4. Risk**

Risk представляет собой отдельный риск.

Типичный состав:

title

description

severity

probability

impact

recommendation

**8.5. Watch Item**

Watch Item описывает показатель, требующий внимания пользователя.

Типичный состав:

title

status

reason

recommendedAction

**8.6. Comparison**

Comparison является новым универсальным объектом версии 1.2.

Назначение:

сравнение двух или нескольких объектов.

Например:

- Иван — Дарья;

- текущая неделя — предыдущая;

- план — факт;

- инвестиции — депозиты.

Типичный состав:

title

items

summary

Каждый элемент массива **items** содержит:

label

value

Renderer самостоятельно выбирает способ отображения:

- таблица;

- карточки;

- диаграмма;

- горизонтальная шкала.

**8.7. Distribution**

Distribution является новым универсальным объектом версии 1.2.

Назначение:

представление структуры одного показателя.

Например:

структура капитала семьи.

Типичный состав:

title

items

total

Каждый элемент массива содержит:

label

value

share

Renderer может использовать:

- круговую диаграмму;

- donut chart;

- stacked bar;

- таблицу.

Способ отображения определяется Renderer.

**8.8. Time Series**

Time Series является новым объектом версии 1.2.

Он предназначен для хранения исторических данных.

Типичный состав:

title

metric

points

Каждая точка содержит:

date

value

Time Series не содержит информации о визуальном оформлении.

Он представляет исключительно данные.

**8.9. Event**

Event используется для описания значимых финансовых событий.

Например:

- покупка недвижимости;

- закрытие кредита;

- получение дивидендов;

- переоценка инвестиций.

Типичный состав:

date

title

description

impact

В дальнейшем Event может использоваться Renderer для построения временных шкал, однако сама схема не зависит от способа отображения.

**9. Принципы расширения аналитических объектов**

Все универсальные объекты могут свободно использоваться внутри любых разделов отчета.

Например:

- Executive Summary может содержать Metric, Insight и Recommendation.

- Раздел "Инвестиции" может использовать Distribution и Time Series.

- Раздел "Семейный капитал" может использовать Comparison.

- Раздел "Точки внимания" может использовать Watch Item и Risk.

Не допускается создание специализированных объектов, если существующий универсальный объект уже решает поставленную задачу.

При разработке новых версий спецификации приоритет всегда отдается расширению существующих универсальных объектов, а не увеличению количества специализированных структур.

**10. Объекты визуализации**

**10.1. Общие положения**

Версия 1.2 впервые вводит понятие **объектов визуализации**.

Объекты визуализации не являются пользовательским интерфейсом.

Они не содержат:

- HTML;

- CSS;

- SVG;

- JavaScript;

- описание конкретного дизайна.

Их назначение — предоставить Renderer дополнительную информацию о том, **каким способом предпочтительно представить аналитические данные пользователю**.

Таким образом, AI продолжает заниматься исключительно аналитикой, а Renderer сохраняет полный контроль над пользовательским интерфейсом.

**10.2. Раздел Visualization**

Все рекомендации по визуальному представлению группируются внутри объекта:

visualizations

Каждый элемент массива является независимым объектом визуализации.

Например:

visualizations

visualization

visualization

visualization

Отсутствие раздела visualizations не считается ошибкой.

Renderer обязан корректно сформировать отчет исключительно на основании аналитических данных.

**10.3. Назначение объекта Visualization**

Visualization описывает:

- какой аналитический объект желательно визуализировать;

- какой тип визуального представления рекомендуется использовать;

- какие данные относятся к данной визуализации.

Visualization **не определяет внешний вид**.

Он определяет только аналитическую модель отображения.

**10.4. Общая структура Visualization**

Типичная структура объекта:

id

title

target

type

data

Назначение полей:

| **Поле** | **Назначение**                 |
|----------|--------------------------------|
| id       | уникальный идентификатор       |
| title    | заголовок                      |
| target   | ссылка на аналитический объект |
| type     | рекомендуемый тип визуализации |
| data     | данные визуализации            |

Renderer может проигнорировать рекомендации по визуализации, если данный тип отображения не поддерживается.

**10.5. Принцип независимости**

Visualization никогда не дублирует аналитические данные.

Он ссылается на уже существующие объекты.

Например:

Distribution

│

▼

Visualization

│

▼

Renderer

Это исключает появление двух различных источников данных.

**11. Типы визуализации**

Версия 1.2 определяет стандартный перечень аналитических способов отображения информации.

Данный перечень является открытым и может расширяться в будущих версиях.

**11.1. KPI**

Используется для отображения одного ключевого показателя.

Например:

- Net Worth

- Wealth Score

- ROI

- Cash Flow

- Passive Income

Renderer самостоятельно определяет способ оформления KPI.

Например:

- карточка;

- плитка;

- компактный индикатор.

**11.2. Comparison**

Предназначен для сравнения нескольких величин.

Например:

- Иван / Дарья;

- План / Факт;

- Неделя 1 / Неделя 2.

Renderer самостоятельно выбирает способ отображения:

- горизонтальные карточки;

- таблица;

- bar chart;

- ranking.

**11.3. Distribution**

Используется для отображения структуры показателя.

Например:

структура капитала семьи.

Допустимые варианты отображения:

- Pie;

- Donut;

- Stacked Bar;

- Table.

Выбор Renderer зависит от пользовательского интерфейса.

**11.4. Trend**

Используется для отображения динамики.

Источник данных:

Time Series.

Допустимые варианты отображения:

- Line Chart;

- Area Chart;

- Sparkline.

**11.5. Waterfall**

Используется для объяснения изменения некоторого показателя.

Например:

Изменение капитала семьи.

Отображает вклад отдельных факторов.

Типичные элементы:

- стартовое значение;

- положительные изменения;

- отрицательные изменения;

- итоговое значение.

**11.6. Allocation**

Используется для отображения распределения капитала.

Например:

- недвижимость;

- депозиты;

- инвестиции;

- ликвидность.

Allocation отличается от Distribution тем, что отражает распределение ресурсов между классами активов.

**11.7. Timeline**

Используется для отображения последовательности событий.

Источник данных:

Event.

Renderer может построить:

- вертикальную временную шкалу;

- горизонтальную шкалу;

- карточки событий.

**11.8. Gauge**

Используется для отображения интегральной оценки.

Например:

- Wealth Score;

- Financial Health;

- Risk Score.

Gauge представляет собой аналитическую сущность.

Конкретная форма отображения определяется Renderer.

**11.9. Progress**

Используется для отображения степени достижения некоторой цели.

Например:

- финансовая цель;

- накопление капитала;

- выполнение бюджета.

**12. Chart**

**12.1. Назначение**

Chart является универсальным контейнером данных для построения диаграмм.

Chart не является описанием SVG.

Chart не является описанием HTML.

Chart содержит исключительно аналитические данные.

**12.2. Общая структура**

Типичная структура Chart:

title

type

series

labels

Версия 1.2 допускает произвольное количество рядов данных.

Каждый ряд представляет самостоятельную аналитическую сущность.

**12.3. Series**

Series представляет один набор данных.

Типичная структура:

name

values

Допускается несколько Series внутри одного Chart.

Например:

Доходы

Расходы

Инвестиции

**12.4. Labels**

Labels определяют подписи категорий.

Например:

Январь

Февраль

Март

или

Недвижимость

Инвестиции

Депозиты

**12.5. Независимость от визуального оформления**

Chart никогда не содержит:

- координат;

- размеров;

- цветов;

- толщины линий;

- оформления легенды;

- расположения подписей.

Все перечисленные параметры относятся исключительно к Renderer.

**13. Display Metadata**

Версия 1.2 вводит необязательный объект:

display

Display Metadata содержит рекомендации по отображению отдельных аналитических объектов.

Display Metadata не является обязательным.

Renderer может полностью игнорировать его.

**13.1. Назначение**

Display Metadata позволяет AI передавать дополнительный аналитический контекст.

Например:

предпочтительный формат отображения.

**13.2. Возможные поля**

Например:

preferredVisualization

importance

precision

unit

compact

Данный перечень не является фиксированным.

**13.3. Ограничения**

Display Metadata не может содержать:

- HTML;

- CSS;

- SVG;

- JavaScript;

- размеры элементов;

- цвета интерфейса;

- параметры анимации.

Display Metadata относится исключительно к аналитическим рекомендациям.

**14. Ответственность Renderer**

Получив AI Report Schema, Renderer обязан:

- корректно обработать все известные объекты;

- безопасно игнорировать неизвестные поля;

- использовать Display Metadata при наличии поддержки;

- сохранить работоспособность при отсутствии раздела visualizations;

- обеспечить корректное отображение всех аналитических данных независимо от наличия объектов визуализации.

Renderer не обязан поддерживать все существующие типы визуализации.

Если конкретный тип не реализован, Renderer должен использовать наиболее близкое универсальное представление (например, таблицу или карточки), не теряя содержащихся в объекте данных.

**15. Правила расширения схемы**

**15.1. Общие принципы**

AI Report Schema проектируется как долговременный контракт обмена данными между аналитическим модулем и пользовательскими интерфейсами.

При развитии схемы должны соблюдаться следующие принципы:

- обратная совместимость;

- постепенная эволюция;

- отсутствие дублирования данных;

- независимость от реализации Renderer;

- независимость от конкретной LLM.

**15.2. Добавление новых объектов**

Допускается добавление:

- новых разделов;

- новых аналитических объектов;

- новых типов визуализации;

- новых необязательных полей.

При этом существующие объекты не должны изменять свое назначение.

**15.3. Удаление объектов**

Удаление объектов допускается только при выпуске новой мажорной версии спецификации.

Версии семейства **1.x** не должны удалять существующие сущности.

**15.4. Изменение структуры**

Изменение структуры существующего объекта допускается только путем добавления новых необязательных полей.

Не допускается:

- изменение смысла существующих полей;

- изменение типа существующих полей;

- изменение обязательности существующих полей.

**15.5. Неизвестные поля**

Все Renderer должны придерживаться следующего правила:

**Любое неизвестное поле должно безопасно игнорироваться без возникновения ошибок.**

Это обеспечивает возможность постепенного обновления различных компонентов проекта.

**16. Требования к разработчикам AI**

При формировании AI Report Schema языковая модель должна соблюдать следующие правила.

**16.1. Не изменять финансовые показатели**

LLM не должна:

- пересчитывать значения;

- корректировать показатели;

- заменять исходные числа;

- округлять значения без необходимости.

Все числовые данные должны соответствовать информации, полученной в составе AI Job Package.

**16.2. Анализировать, а не пересказывать**

Основная задача AI заключается не в повторении финансовых показателей, а в формировании аналитической ценности.

Приоритет имеют:

- объяснение причин изменений;

- выявление закономерностей;

- оценка влияния событий;

- определение рисков;

- формирование рекомендаций.

Текст не должен дублировать очевидные числовые значения без добавления аналитического контекста.

**16.3. Максимальная структурированность**

Если информация может быть представлена структурированным объектом, следует использовать структуру вместо свободного текста.

Например:

предпочтительно вернуть объект **Risk**, чем абзац текста о риске.

Предпочтительно вернуть **Distribution**, чем текстовое описание структуры капитала.

Предпочтительно вернуть **Comparison**, чем перечисление сравниваемых значений.

**16.4. Использование объектов визуализации**

Если аналитический вывод естественным образом может быть представлен визуально, рекомендуется дополнительно сформировать соответствующий объект в разделе visualizations.

При этом отсутствие объекта визуализации не считается ошибкой.

**17. Требования к разработчикам Renderer**

Renderer является единственным компонентом проекта, отвечающим за визуальное представление AI Report Schema.

**17.1. Принцип единственной ответственности**

Renderer не должен:

- выполнять финансовые расчеты;

- изменять аналитические выводы;

- интерпретировать финансовые показатели;

- генерировать новые аналитические данные.

Единственная задача Renderer — преобразование AI Report Schema в пользовательское представление.

**17.2. Универсальность**

Renderer должен стремиться использовать универсальные механизмы отображения вместо специализированной логики для отдельных разделов.

Предпочтительно реализовывать поддержку:

- Metric;

- Insight;

- Recommendation;

- Risk;

- Comparison;

- Distribution;

- Time Series;

- Event;

- Chart.

Это позволяет автоматически поддерживать новые разделы отчета без существенного изменения Renderer.

**17.3. Отказоустойчивость**

Renderer обязан корректно работать при:

- отсутствии необязательных разделов;

- отсутствии объектов визуализации;

- наличии неизвестных полей;

- наличии новых объектов, появившихся в будущих версиях спецификации.

Наличие неподдерживаемого объекта не должно приводить к невозможности формирования отчета.

**17.4. Приоритет отображения**

При построении пользовательского интерфейса рекомендуется придерживаться следующего порядка представления информации:

1.  ключевые показатели (KPI);

2.  визуальная аналитика;

3.  краткие аналитические выводы;

4.  подробные пояснения;

5.  рекомендации.

Данный порядок соответствует принципам представления информации, закрепленным в Project Handbook.

**18. Совместимость между версиями**

**18.1. Совместимость v1.1 → v1.2**

Любой документ, соответствующий версии 1.1, автоматически считается корректным документом версии 1.2.

Никаких обязательных изменений существующих AI Report Schema не требуется.

**18.2. Совместимость Renderer**

Renderer версии 1.2 должен поддерживать:

- документы версии 1.1;

- документы версии 1.2;

- документы, содержащие только часть новых возможностей версии 1.2.

**18.3. Совместимость AI**

LLM может постепенно внедрять новые аналитические объекты.

Использование новых объектов является рекомендуемым, но не обязательным.

**19. Рекомендации по развитию спецификации**

Следующие направления развития рассматриваются как приоритетные для будущих версий:

- расширение поддержки исторических данных;

- развитие объектов визуализации;

- новые типы аналитических сравнений;

- поддержка интерактивных пользовательских интерфейсов;

- дополнительные аналитические сущности Family Office;

- развитие поддержки долгосрочного финансового планирования.

При этом фундаментальная архитектура AI Report Schema должна оставаться неизменной.

**20. Заключение**

AI Report Schema является центральным контрактом обмена аналитическими данными проекта Family Budget Automation.

Настоящая спецификация обеспечивает разделение ответственности между всеми компонентами системы:

- **Google Sheets** отвечает за финансовые расчеты;

- **AI** выполняет аналитическую обработку данных;

- **AI Report Schema** определяет единый формат обмена аналитической информацией;

- **Renderer** преобразует аналитические данные в пользовательское представление;

- **HTML Template** определяет внешний вид отчета.

Версия **1.2** развивает спецификацию версии **1.1**, сохраняя полную обратную совместимость и закладывая архитектурную основу для следующего этапа развития проекта — **визуальной аналитики**.

Главной особенностью версии 1.2 является переход от восприятия AI Report Schema как структуры данных к пониманию ее как **универсального контракта между аналитическим модулем и любым пользовательским интерфейсом проекта**.

Этот подход обеспечивает:

- независимость аналитики от способов отображения;

- независимость Renderer от конкретной языковой модели;

- возможность появления новых пользовательских интерфейсов без изменения логики AI;

- масштабируемость проекта;

- долгосрочную устойчивость архитектуры.

Таким образом, AI Report Schema становится не просто форматом обмена JSON-документами, а одним из фундаментальных архитектурных компонентов Family Budget Automation, определяющим взаимодействие между интеллектуальным анализом и пользовательским опытом.
