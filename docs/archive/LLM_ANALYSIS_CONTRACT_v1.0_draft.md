# 1. Назначение документа

Настоящий документ определяет целевой контракт обмена данными между языковой моделью (LLM) и модулем ReportBuilder.gs (Apps Script).

LLM Analysis является минимальным JSON-документом, содержащим структурированную аналитическую интерпретацию данных, сгенерированную LLM на основе AI Job Package. Контракт содержит текстовые аналитические поля и ограниченный набор служебных enum/key-полей, необходимых для машинной обработки.

Данный контракт определяет:

> 1\. структуру ответа LLM;
>
> 2\. правила заполнения полей;
>
> 3\. границы числовой ответственности LLM;
>
> 4\. принципы расширения;
>
> 5\. требования к совместимости между версиями;
>
> 6\. правила взаимодействия между LLM и ReportBuilder.

*Контракт не зависит от конкретной LLM и не содержит требований к визуализации.*

# 3. Основные принципы

## 3.1. LLM является аналитиком

LLM выполняет аналитическое reasoning над данными, переданными в AI Job Package.

LLM может:

- сравнивать показатели между периодами и участниками;

- выявлять тренды, аномалии и разнонаправленную динамику;

- объяснять взаимосвязи между показателями;

- формировать гипотезы о причинах изменений;

- оценивать риски и относительную значимость событий;

- формировать рекомендации и точки внимания;

- синтезировать несколько фактов в единый аналитический вывод.

LLM не является расчетным слоем, источником финансовых показателей или владельцем структуры пользовательского отчета.

## 3.2. Numerical Authority: Google Sheets владеет числами

Google Sheets остается единственным источником финансовых данных, расчетов и числовых финансовых показателей проекта.

LLM может использовать числовые значения из AI Job Package для сравнения, интерпретации, выявления закономерностей, оценки относительной значимости и формирования текстовых выводов.

LLM может ссылаться в текстовой аналитике на числовое значение только если это значение явно присутствует в AI Job Package. Такое упоминание не делает LLM источником числа.

LLM не должна возвращать новый числовой финансовый показатель, полученный путем собственного расчета, преобразования, агрегации, округления, экстраполяции, прогнозирования или применения внешнего допущения.

В частности, LLM не должна самостоятельно создавать:

- новые суммы, проценты, коэффициенты и доли;

- доходность, ROI, IRR и иные производные метрики;

- упущенный доход или ожидаемый процентный доход;

- новые план/факт отклонения;

- прогнозные значения капитала, доходов, расходов или ликвидности;

- количественные целевые значения, ставки, пороги или диапазоны, отсутствующие во входных данных.

**Принцип контракта: AI owns meaning. Sheets own numbers.**

## 3.3. Минимальный контракт

Контракт содержит только поля, необходимые для передачи аналитического смысла от LLM к ReportBuilder. Числовые KPI, исторические ряды и другие финансовые структуры в LLM Analysis не дублируются.

Это обеспечивает стабильность генерации, простоту валидации, предсказуемость результата и минимизирует риск появления второго источника истины.

## 3.4. Правило No Repeat

LLM должна минимизировать содержательное дублирование между блоками. Каждый аналитический тезис имеет один основной блок.

Допускается использование одного и того же финансового события в разных блоках только при различной функции:

- **executiveSummary —** синтез общей картины;

- **insights —** объяснение события или закономерности;

- **recommendations —** конкретное действие;

- **watchItems —** контекст контролируемого показателя;

- **personAnalysis —** аспект, специфичный для конкретного человека.

Запрещено дословное или практически дословное повторение одного и того же вывода в нескольких блоках.

## 3.5. Качественные критерии и защитные максимумы

Количество элементов определяется насыщенностью периода, а не обязательным минимумом. LLM не должна генерировать выводы или рекомендации только для заполнения квоты.

Критерий включения элемента: значимое событие, закономерность, риск или действие, которое добавляет аналитическую ценность по сравнению с простым просмотром исходных таблиц.

Для защиты стабильности и длины ответа контракт устанавливает только максимальные размеры массивов.

## 3.6. Независимость от LLM

Контракт не зависит от конкретной языковой модели. Допускается использование OpenAI, Anthropic, Google, DeepSeek, локальных моделей и будущих моделей при условии соблюдения настоящего контракта.

## 3.7. Расширяемость

Будущие версии могут добавлять новые необязательные поля и enum-значения, но не должны менять смысл существующих полей без изменения версии контракта. Удаление полей, изменение их типов или семантики является breaking change.

## 3.8. Grounded Analysis

Каждый вывод LLM должен опираться на данные или контекст, присутствующие в AI Job Package. Если данных недостаточно, LLM должна опустить вывод, а не заполнять пробел предположением.

Качественные гипотезы допускаются только как гипотезы и не должны формулироваться как подтвержденный финансовый факт.

# 4. Общая структура LLM Analysis

{  
"executiveSummary": "",  
"insights": \[\],  
"recommendations": \[\],  
"watchItems": \[\],  
"personAnalysis": \[\]  
}

Все пять верхнеуровневых полей являются обязательными. Если значимой аналитики для блока нет, используется пустая строка или пустой массив. LLM не должна удалять верхнеуровневые поля и не должна добавлять новые поля в рамках версии 1.0.

# 5. Поля контракта

## 5.1. executiveSummary

| **Параметр**   | **Значение**                                         |
|----------------|------------------------------------------------------|
| Тип            | string                                               |
| Обязательность | обязательное поле; может быть пустой строкой         |
| Длина          | если непустое: рекомендуется 50–500 символов         |
| Назначение     | краткий синтез финансового состояния семьи за период |

Правила:

- профессиональный, нейтральный стиль;

- отражает общую картину периода;

- не превращается в перечень KPI;

- может ссылаться на числовые значения только при их явном наличии в AI Job Package;

- не содержит новых числовых показателей, рассчитанных LLM;

- не повторяет дословно отдельные insights.

Пример:

{  
"executiveSummary": "Финансовое состояние семьи улучшилось, однако динамика участников была разнонаправленной. Основная зона внимания — отрицательное необъясненное изменение капитала и рост бездействующих остатков."  
}

## 5.2. insights

Тип: array of objects. Максимум: 5 элементов.

| **Поле** | **Тип** | **Обязательность** | **Назначение**                  |
|----------|---------|--------------------|---------------------------------|
| text     | string  | да                 | законченный аналитический вывод |
| category | enum    | да                 | семантическая категория вывода  |

Допустимые category: positive, negative, neutral.

Правила:

- каждый insight — одна законченная мысль, обычно 1–3 предложения;

- вывод должен объяснять значимое событие, закономерность или взаимосвязь;

- LLM может сопоставлять несколько входных чисел для смыслового вывода;

- если insight цитирует число, оно должно присутствовать в AI Job Package;

- не допускаются новые рассчитанные LLM числовые метрики.

{  
"insights": \[  
{  
"text": "Рост семейного капитала обеспечен положительной динамикой мужа, тогда как капитал жены двигался в противоположном направлении.",  
"category": "neutral"  
},  
{  
"text": "Необъясненное изменение капитала перешло в отрицательную зону, что требует сверки операций и источников движения средств.",  
"category": "negative"  
}  
\]  
}

## 5.3. recommendations

Тип: array of objects. Максимум: 7 элементов.

| **Поле** | **Тип** | **Обязательность** | **Назначение**      |
|----------|---------|--------------------|---------------------|
| text     | string  | да                 | конкретное действие |
| priority | enum    | да                 | приоритет действия  |

Допустимые priority: high, medium, low.

Правила:

- каждая рекомендация должна быть конкретным и исполнимым действием;

- рекомендация должна следовать из данных или пользовательского контекста;

- LLM не должна изобретать количественные цели, ставки, ожидаемую доходность, диапазоны или пороги;

- количественное значение допустимо только как ссылка на значение, уже присутствующее в AI Job Package или USER CONTEXT;

- рекомендация не должна быть простым повтором insight.

{  
"recommendations": \[  
{  
"text": "Провести сверку операций за период для выявления источника необъясненного изменения капитала.",  
"priority": "high"  
},  
{  
"text": "Проверить возможность размещения бездействующих остатков в доступном доходном инструменте с учетом условий, уже отраженных в исходных данных.",  
"priority": "medium"  
}  
\]  
}

## 5.4. watchItems

Тип: array of objects. Максимум: 4 элемента.

| **Поле** | **Тип** | **Обязательность** | **Назначение**                                    |
|----------|---------|--------------------|---------------------------------------------------|
| key      | enum    | да                 | машинный идентификатор контролируемого показателя |
| context  | string  | да                 | аналитический контекст                            |
| severity | enum    | да                 | уровень важности                                  |

Допустимые значения key версии 1.0:

- unexplained_change — необъясненное изменение капитала;

- idle_cash — бездействующие деньги;

- missed_interest — упущенный процентный доход, если сам показатель рассчитан в Google Sheets;

- budget_overrun — превышение плановых расходов;

- concentration_risk — риск концентрации активов;

- debt_dynamics — динамика долговой нагрузки.

LLM не формирует новые значения key. Если выявленный риск не соответствует перечисленным ключам, он должен быть представлен через insights, recommendations или personAnalysis. Добавление нового watchItems.key требует новой версии контракта и поддержки ReportBuilder.

Допустимые severity: critical, high, medium, low.

{  
"watchItems": \[  
{  
"key": "unexplained_change",  
"context": "Показатель сменил направление и требует проверки полноты учтенных движений средств.",  
"severity": "critical"  
},  
{  
"key": "idle_cash",  
"context": "Бездействующие остатки продолжают расти и одновременно снижается доля средств в доходных инструментах.",  
"severity": "high"  
}  
\]  
}

## 5.5. personAnalysis

Тип: array of objects. Максимум: 2 элемента; не более одного объекта для каждого person.

| **Поле**      | **Тип**         | **Обязательность** | **Назначение**                       |
|---------------|-----------------|--------------------|--------------------------------------|
| person        | enum            | да                 | husband или wife                     |
| insights      | array\[string\] | да                 | персональные наблюдения, максимум 4  |
| risks         | array\[string\] | да                 | персональные риски, максимум 4       |
| opportunities | array\[string\] | да                 | персональные возможности, максимум 4 |

Правила:

- массив может быть пустым, если значимой персональной аналитики нет;

- каждый объект относится только к одному члену семьи;

- общесемейные выводы не должны дублироваться без персонального аспекта;

- числовые значения могут упоминаться только если они явно переданы в AI Job Package;

- риски и возможности не должны содержать придуманные количественные цели или прогнозы.

{  
"person": "husband",

\],

"Снизить объем средств, не выполняющих определенную финансовую функцию."  
\]  
},  
{  
"person": "wife",

"Снижение капитала происходит одновременно с ростом бездействующих остатков."

# 6. Связь с Report Model

LLM Analysis используется ReportBuilder для формирования текстовой части компонентов Report Model. Числовые поля Report Model формируются исключительно из авторитетных данных Google Sheets.

| **Поле LLM Analysis**             | **Целевое использование в Report Model**                                    |
|-----------------------------------|-----------------------------------------------------------------------------|
| executiveSummary                  | text_block (executive summary)                                              |
| insights                          | insight_list                                                                |
| recommendations                   | recommendation_list                                                         |
| watchItems                        | watch_item; числовые данные добавляет ReportBuilder из Google Sheets по key |
| personAnalysis\[i\].insights      | insight_list внутри section                                                 |
| personAnalysis\[i\].risks         | insight_list внутри section с семантикой риска                              |
| personAnalysis\[i\].opportunities | insight_list внутри section с семантикой возможности                        |

Примечание: настоящий контракт не определяет визуальное оформление персональных risks/opportunities. ReportBuilder выполняет только детерминированное преобразование структуры; Renderer определяет представление в соответствии с Report Model Specification.

Ключевой принцип: LLM Analysis поставляет аналитический смысл; Google Sheets поставляет числа; ReportBuilder соединяет эти два слоя, но не выполняет финансовый анализ.

# 7. Обработка пользовательского контекста

AI Job Package может содержать раздел \# USER CONTEXT с пояснениями пользователя к административным изменениям, ручным переоценкам, новым счетам и другим событиям, которые не должны интерпретироваться как самостоятельное финансовое событие.

Правила:

> 1\. LLM обязана учитывать USER CONTEXT;
>
> 2\. не должна трактовать объясненное административное изменение как необъясненный финансовый риск;
>
> 3\. не должна генерировать алерт только на основании административного действия;
>
> 4\. не возвращает USER CONTEXT как отдельный выходной блок;
>
> 5\. может ссылаться на количественные правила из USER CONTEXT только если они явно заданы пользователем;
>
> 6\. не выводит из USER CONTEXT новые числа или финансовые показатели.

# 8. Обработка исторических данных

AI Job Package может содержать раздел \# HISTORICAL DATA с агрегированными историческими данными и временным рядом. Текущая проектная версия контракта ориентируется на историю до 12 недель, если такой объем передан во входных данных.

Правила анализа истории:

> 1\. выявлять тренды, развороты, устойчивые последовательности и аномалии;
>
> 2\. сопоставлять текущий период с историческим контекстом;
>
> 3\. не создавать собственные числовые пороги значимости;
>
> 4\. не рассчитывать новые статистические или финансовые показатели, отсутствующие во входных данных;
>
> 5\. не формировать числовые прогнозы;
>
> 6\. допускаются качественные forward-looking гипотезы о направлении или риске только с явной формулировкой неопределенности.

Пример допустимой формулировки: «Если текущая динамика сохранится, риск дальнейшего роста бездействующих остатков остается повышенным». Такая фраза является качественной гипотезой, а не числовым прогнозом.

# 10. Требования к LLM

LLM обязана:

> 1\. возвращать только валидный JSON;
>
> 2\. возвращать все пять верхнеуровневых полей;
>
> 3\. соблюдать типы полей и допустимые enum/key-значения;
>
> 4\. основывать каждый вывод на AI Job Package;
>
> 5\. использовать входные числа для аналитического reasoning;
>
> 6\. цитировать числовые значения только если они явно присутствуют во входных данных;
>
> 7\. соблюдать правило No Repeat;
>
> 8\. учитывать USER CONTEXT;
>
> 9\. явно отделять гипотезу от подтвержденного факта;
>
> 10\. не включать HTML или Markdown.

LLM не должна:

> 1\. создавать новые числовые финансовые показатели;
>
> 2\. самостоятельно рассчитывать суммы, проценты, коэффициенты, доходность, отклонения или прогнозы для вывода пользователю;
>
> 3\. изменять, округлять или заменять значения из AI Job Package так, чтобы менялся их смысл;
>
> 4\. изобретать ставки, пороги, количественные цели или диапазоны;
>
> 5\. генерировать визуализации, HTML или Report Model;
>
> 6\. принимать решение о структуре пользовательского отчета;
>
> 7\. возвращать поля, отсутствующие в контракте v1.0;
>
> 8\. маскировать недостаток данных уверенной формулировкой.

# 11. Требования к ReportBuilder

ReportBuilder обязан:

> 1\. читать LLM Analysis из файла llm_analysis.json;
>
> 2\. валидировать JSON и структуру контракта;
>
> 3\. связывать watchItems.key с соответствующими числовыми данными Google Sheets;
>
> 4\. формировать компоненты Report Model;
>
> 5\. добавлять финансовые числа только из Google Sheets или других авторитетных структур, сформированных из Sheets;
>
> 6\. корректно обрабатывать пустые и отсутствующие аналитические блоки;
>
> 7\. логировать отклонения от контракта без остановки формирования числовой части отчета, если это возможно.

ReportBuilder не должен:

> 1\. выполнять финансовый анализ;
>
> 2\. рассчитывать новые финансовые показатели;
>
> 3\. изменять смысл текстовых выводов LLM;
>
> 4\. дописывать отсутствующие insights или recommendations;
>
> 5\. подменять неизвестные enum-значения значениями по умолчанию, если это меняет смысл;
>
> 6\. добавлять числовые значения внутрь текстовых полей LLM.

ReportBuilder выполняет детерминированную сборку модели, а не интерпретацию финансового смысла.

# 12. Валидация ответа LLM

## 12.1. Структурная валидация

- ответ является валидным JSON;

- присутствуют executiveSummary, insights, recommendations, watchItems, personAnalysis;

- типы полей соответствуют спецификации;

- внутренние обязательные поля элементов присутствуют.

## 12.2. Валидация enum/key-полей

- category ∈ {positive, negative, neutral};

- priority ∈ {high, medium, low};

- severity ∈ {critical, high, medium, low};

- person ∈ {husband, wife};

- watchItems.key ∈ {unexplained_change, idle_cash, missed_interest, budget_overrun, concentration_risk, debt_dynamics}.

## 12.3. Ограничения размера

| **Поле**                          | **Ограничение**                                                         |
|-----------------------------------|-------------------------------------------------------------------------|
| executiveSummary                  | пусто или рекомендуется 50–500 символов; более 500 — невалидно для v1.0 |
| insights                          | 0–5                                                                     |
| recommendations                   | 0–7                                                                     |
| watchItems                        | 0–4                                                                     |
| personAnalysis                    | 0–2                                                                     |
| personAnalysis\[i\].insights      | 0–4                                                                     |
| personAnalysis\[i\].risks         | 0–4                                                                     |
| personAnalysis\[i\].opportunities | 0–4                                                                     |

Минимальное количество аналитических элементов не устанавливается.

## 12.4. Обработка отклонений

> 1\. если верхнеуровневое поле отсутствует, ReportBuilder нормализует его в пустую строку или пустой массив и логирует предупреждение;
>
> 2\. если тип поля неверен, используется пустое значение и логируется ошибка;
>
> 3\. если enum или watchItems.key неизвестен, соответствующий элемент пропускается и логируется предупреждение;
>
> 4\. если массив превышает максимум, используются первые N элементов; превышение логируется;
>
> 5\. если executiveSummary превышает допустимую длину, текстовый блок пропускается; ReportBuilder не редактирует и не сокращает текст автоматически;
>
> 6\. ReportBuilder никогда не дополняет массивы до минимального количества и не генерирует отсутствующую аналитику.

# 13. Правила расширения контракта

## 13.1. Добавление новых полей

Новая версия контракта может добавлять необязательные поля. LLM версии 1.0 не должна возвращать их до официального обновления контракта и ReportBuilder.

Возможные будущие направления, уже рассматривавшиеся проектом: marketCommentary, depositCommentary, investmentCommentary, macroFactors. Их наличие в настоящем документе не означает утверждения этих полей.

## 13.2. Добавление enum/key-значений

Добавление нового значения category, priority, severity, person или watchItems.key требует новой версии контракта и соответствующей поддержки ReportBuilder. Неизвестные значения не должны молча интерпретироваться как существующие.

## 13.3. Обратная совместимость

ReportBuilder будущих версий должен сохранять способность обработать документ версии 1.0. Новые необязательные поля могут игнорироваться старым Renderer только после прохождения через совместимый ReportBuilder/Report Model.

Изменение типа существующего поля, его семантики или удаление поля является breaking change.

# 14. Обработка ошибок и fallback

## 14.1. Невалидный JSON

> 1\. ReportBuilder логирует ошибку;
>
> 2\. используется пустой LLM Analysis;
>
> 3\. Report Model формируется без LLM-аналитики, используя доступные числовые данные Google Sheets;
>
> 4\. ошибка LLM не должна приводить к потере авторитетной числовой части отчета, если она доступна.

## 14.2. Частично невалидный ответ

> 1\. валидные независимые блоки сохраняются;
>
> 2\. невалидные элементы пропускаются;
>
> 3\. каждое отклонение логируется;
>
> 4\. ReportBuilder не пытается восстановить смысл отсутствующего или поврежденного текста.

## 14.3. Недостаток данных

Если LLM не может сформировать обоснованный вывод из AI Job Package, соответствующий массив остается пустым. Пустая аналитика является допустимым результатом и предпочтительнее неподтвержденного вывода.

# 15. Примеры обработки

## 15.1. Минимальный LLM Analysis

{  
"executiveSummary": "",  
"insights": \[\],  
"recommendations": \[\],  
"watchItems": \[\],  
"personAnalysis": \[\]  
}

ReportBuilder формирует Report Model без LLM-аналитики. Числовые компоненты, доступные из Google Sheets, продолжают формироваться.

## 15.2. Частичный LLM Analysis

{  
"executiveSummary": "",  
"insights": \[  
{  
"text": "Необъясненное изменение капитала перешло в отрицательную зону и требует проверки источников движения средств.",  
"category": "negative"  
}  
\],  
"recommendations": \[\],  
"watchItems": \[\],  
"personAnalysis": \[\]  
}

ReportBuilder формирует insight_list. Остальные текстовые блоки отсутствуют.

## 15.3. Допустимое использование числа

Если AI Job Package явно содержит финансовое значение, LLM может процитировать это же значение в тексте без пересчета. Например, если входные данные уже содержат показатель «доля недвижимости = 71%», допустима формулировка «Доля недвижимости 71% создает концентрационный риск».

Если входные данные содержат только стоимость недвижимости и общий капитал, LLM не должна самостоятельно рассчитывать 71% и возвращать это значение как финансовый факт.

## 15.4. Недопустимый новый расчет

Если AI Job Package содержит сумму бездействующих денег и процентную ставку, но не содержит рассчитанного годового упущенного дохода, LLM не должна самостоятельно рассчитывать и возвращать такой годовой доход. Она может рекомендовать проверить размещение бездействующих средств или сослаться на показатель missed_interest, если он уже рассчитан в Google Sheets и передан во входных данных.

# 16. Заключение

LLM Analysis Contract v1.0 разделяет аналитический смысл и числовую финансовую истину.

Контракт обеспечивает:

> 1\. максимальное использование сильных сторон LLM для интерпретации, синтеза и поиска закономерностей;
>
> 2\. сохранение Google Sheets как единственного источника финансовых чисел и расчетов;
>
> 3\. отсутствие второго расчетного слоя внутри AI;
>
> 4\. предсказуемую структуру JSON и простой fallback;
>
> 5\. детерминированную сборку Report Model через ReportBuilder;
>
> 6\. расширяемость без потери аудируемости.

**Фундаментальный принцип версии 1.0:**

**AI owns meaning. Sheets own numbers.**
