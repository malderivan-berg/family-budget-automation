# **ЧАСТЬ I. ОПИСАНИЕ ПРОЕКТА**

## 1. Назначение проекта

**Family Budget Automation** — это программная система для автоматизированного ведения семейного бюджета, анализа личного капитала и формирования профессиональных финансовых отчетов уровня Family Office.

Проект не является системой бухгалтерского учета или банкинга. Его основная задача — автоматизировать подготовку финансовой аналитики и ввод данных при сохранении полного контроля пользователя над финансовыми показателями.

## 2. Видение проекта (Vision)

Конечная цель — создание персонального финансового ИИ-ассистента семьи. Пользователь не должен заниматься техническими операциями по подготовке отчетов или ручному вводу рутинных данных. Взаимодействие с системой сводится к естественному диалогу (текст/голос через Telegram), а все этапы обработки информации выполняются системой автоматически.

## 3. Миссия проекта

Предоставить семье инструмент, позволяющий регулярно получать объективную, прозрачную и профессиональную оценку своего финансового состояния без необходимости вручную выполнять сложную обработку данных, объединяя возможности Google Sheets, Google Apps Script, внешних оркестраторов (Nodul) и современных языковых моделей (LLM).

## 4. Главные цели проекта

> 1\. **Автоматизация:** Максимальное сокращение ручных действий. Каждая новая версия должна уменьшать объем ручной работы.
>
> 2\. **Надежность:** Любое архитектурное решение должно обеспечивать предсказуемость. Надежность всегда имеет приоритет над производительностью или скоростью внедрения.
>
> 3\. **Прозрачность:** Пользователь должен понимать происхождение каждого финансового показателя. Ни один числовой показатель не должен вычисляться "внутри ИИ".
>
> 4\. **Масштабируемость:** Система должна позволять добавлять новые виды аналитики, интерфейсы и модели ИИ без переработки существующей архитектуры.
>
> 5\. **Независимость:** Проект не должен зависеть от конкретной LLM, AI-оркестратора, HTML-шаблона или мессенджера. Все компоненты взаимодействуют исключительно через официальные контракты.
>
> 6\. **Визуальная аналитика:** Предпочтение визуальному представлению аналитики (KPI, диаграммы, индикаторы) перед текстовым описанием, если это позволяет эффективнее передать смысл.

## 5. Основные принципы проекта (Приоритеты)

Все технические решения принимаются в строгом порядке приоритетов. Ни одно решение не должно нарушать более высокий приоритет ради достижения более низкого.

| **Приоритет** | **Принцип**                   | **Описание**                                                                                       |
|---------------|-------------------------------|----------------------------------------------------------------------------------------------------|

| **2**         | **Простота**                  | Минимальные изменения, отсутствие дублирования кода, читаемость, отсутствие "магических значений". |
| **3**         | **Масштабируемость**          | Модульность, заменяемость компонентов, расширяемость контрактов.                                   |
| **4**         | **Автоматизация**             | Сокращение ручных шагов, но *только* при соблюдении приоритета 1 (Надежность).                     |
| **5**         | **Пользовательская ценность** | Удобство UX/UI, скорость получения результата, естественность взаимодействия.                      |

## 8. Главный архитектурный принцип: Единственное направление движения данных

Во всей системе данные проходят только вперед в рамках своего конвейера. Обратные зависимости между слоями архитектуры не допускаются.

• Outbound Pipeline: Данные → Расчеты (Google Sheets) → Экспорт → LLM (Анализ) → HTML → Telegram.

• Inbound Voice Pipeline: Telegram Voice → STT → LLM NER → Nodul Assemble Full Batch → Draft → Подтверждение пользователя → Apps Script → Google Sheets.

• Voice Notification Pipeline: Apps Script → Voice/Outbox → Nodul → Telegram → notification_sent ACK → Apps Script cleanup.

LLM в inbound voice pipeline не создает полный Voice Transaction Batch и не принимает решения о записи. LLM возвращает только структурированный результат NER. Полный batch собирается Nodul, а окончательная нормализация, валидация, идемпотентность и запись выполняются Apps Script.

## 11. Voice Transaction Batch Schema

### 11.1 Назначение

Voice Transaction Batch Schema v2.0 является официальным runtime-контрактом хранения и передачи структурированного результата голосового ввода между Nodul и Apps Script до записи операции в Google Sheets.

Контракт относится только к голосовому вводу фактических финансовых операций.

Voice pipeline v2.0 не используется для создания или изменения плановых операций, поиска существующего плана, fuzzy matching, update_planned или финансовых расчетов.

Google Sheets остается единственным источником финансовых данных и расчетов.

### 11.2 Область применения

Целевая цепочка обработки:

Telegram Voice  
↓  
STT → transcript  
↓  
LLM NER → operations\[{date, amount, type, comment}\]  
↓  
Nodul Assemble Full Batch  
↓  
Voice/Drafts/{batch_id}.json  
↓ user confirms  
Voice/Callbacks/{batch_id}\_confirm.json  
↓  
Apps Script: normalize / owner / operation_id / validate / idempotency  
↓  
Google Sheets — "Календарь"  
├→ Voice/Archive/{batch_id}.json  
└→ Voice/Outbox/voice_notification\_{batch_id}.json  
↓  
Nodul → Telegram  
↓  
Voice/Callbacks/{batch_id}\_notification_sent.json  
↓  
Apps Script cleanup

### 11.3 Разделение ответственности

**11.3.1 STT**

STT отвечает только за преобразование аудио в текст. STT не определяет финансовый смысл операции, owner, type, правила записи или финансовые показатели.

**11.3.2 LLM Voice NER**

LLM выполняет только извлечение структурированных сущностей из TRANSCRIPT.

Допустимый structured output LLM:

{  
"operations": \[  
{  
"date": "DD.MM.YYYY",  
"amount": 1000,  
"type": "Расход",  
"comment": "Краткое описание"  
}  
\]  
}

LLM определяет только date, amount, type, comment и количество операций в сообщении.

LLM не определяет owner, operation_id, intent, target_hint, create_new / update_planned, confidence-based решение о записи, warnings как часть runtime-контракта, цель обновления в Google Sheets или факт записи операции.

Критическое правило type: само наличие суммы не является основанием определить Доход или Расход. Если направление движения денег нельзя определить однозначно, соответствующая operation не создается.

Если валидных операций нет, LLM возвращает:

{"operations":\[\]}

Если в одном сообщении распознано более 5 операций, batch не должен частично обрезаться до первых пяти. LLM возвращает пустой operations; частичный batch запрещен.

**11.3.3 Nodul**

Nodul отвечает за авторизацию Telegram-пользователя, получение voice message, загрузку аудио, вызов STT, чтение актуального voice_ner_prompt.txt, передачу CURRENT_DATE и TRANSCRIPT в LLM, получение structured NER output, сборку полного Voice Transaction Batch v2.0, сохранение Draft, confirmation card, создание confirm callback, доставку итогового voice-уведомления из Outbox и создание notification_sent ACK после успешной доставки.

Nodul не выполняет запись финансовых данных в Google Sheets.

**11.3.4 Apps Script**

Apps Script является валидатором, регистратором и владельцем детерминированных runtime-полей.

1\. нормализация batch;

2\. определение owner по telegram_user_id;

3\. формирование operation_id;

4\. валидация даты, суммы, type и comment;

5\. проверка лимита операций;

6\. идемпотентность;

7\. запись фактической операции в "Календарь";

8\. recovery из Confirmed;

9\. архивирование;

10\. создание итогового Voice/Outbox notification;

11\. обработка notification_sent ACK;

12\. удаление Outbox-файла только после валидного ACK.

Apps Script не выполняет STT, NER или прямые Telegram HTTP-вызовы для voice pipeline.

### 11.4 Паттерн "Распознавание → Структурирование → Подтверждение → Запись"

Согласно приоритету "Надежность \> Автоматизация", распознанная голосовая операция не записывается автоматически.

1\. Распознавание — STT преобразует аудио в текст.

2\. Структурирование — LLM извлекает date / amount / type / comment.

3\. Сборка — Nodul создает Voice Transaction Batch v2.0.

4\. Подтверждение — пользователь проверяет карточку и нажимает "✅ Подтвердить".

5\. Запись — Apps Script валидирует и записывает операцию в Google Sheets.

Cancel не является частью live-runtime v2.0.

Inline-кнопка "✅ Подтвердить" может оставаться видимой после обработки. Повторное нажатие безопасно благодаря идемпотентности.

### 11.5 Canonical Voice Transaction Batch v2.0

{  
"schema_version": "2.0",  
"batch_id": "...",  
"telegram_message_id": "...",  
"telegram_user_id": "...",  
"received_at": "...",  
"stt_result": {  
"provider": "...",  
"transcript": "..."  
},  
"operations": \[  
{  
"date": "DD.MM.YYYY",  
"amount": 1000,  
"type": "Расход",  
"comment": "..."  
}  
\]  
}

Persisted batch не обязан содержать owner или operation_id. Эти поля создаются Apps Script непосредственно перед валидацией и записью.

### 11.6 Детерминированные поля Apps Script

owner определяется только по telegram_user_id на основании конфигурации разрешенных Telegram-пользователей. Допустимые значения: "Муж" и "Жена".

operation_id формируется только Apps Script в формате {telegram_message_id}\_{index}, где index — 0-based индекс операции в batch.

Если legacy batch содержит owner или operation_id, Apps Script не должен доверять этим значениям и формирует их заново.

### 11.7 Нормализация суммы и знаковая конвенция

В Voice Transaction Batch amount представляет абсолютную величину и должен быть больше нуля. Apps Script может нормализовать числовую строку и отрицательное входное значение в положительную абсолютную сумму.

Знак actual_value_RUR определяется только type: Расход → отрицательное значение; Доход → положительное значение.

LLM не является владельцем знаковой конвенции Google Sheets.

### 11.8 Даты

Canonical формат даты voice operation: DD.MM.YYYY. Apps Script дополнительно поддерживает YYYY-MM-DD и нормализует его.

Дата должна быть реальной календарной датой. Относительные даты определяются LLM относительно CURRENT_DATE.

Период назначения платежа не является датой операции. Например, "Заплатил няне 40 тысяч за август" при отсутствии отдельной даты платежа означает date = CURRENT_DATE; comment может содержать "за август".

### 11.9 Ограничения

1\. Максимальное количество операций в одном batch: 5.

2\. Partial batch при распознавании более 5 операций запрещен.

3\. Пустой operations не сохраняется как Draft.

4\. amount = 0 запрещен.

5\. type может быть только "Доход" или "Расход".

6\. comment должен быть непустой строкой.

7\. confidence_score не используется для принятия runtime-решения.

8\. Плановые операции и fuzzy matching не используются.

### 11.10 Идемпотентность

Идемпотентность реализуется на двух уровнях.

Уровень batch: если Archive/{batch_id}.json уже существует, повторный confirm считается idempotent success. Calendar повторно не изменяется, итоговое уведомление повторно не создается и ошибка отсутствующего Draft не генерируется.

Уровень operation: перед записью Apps Script проверяет наличие voice_operation_id в "Календаре". Если все operation_id batch уже существуют в Calendar, batch считается успешно обработанным и может быть архивирован без повторной записи.

### 11.11 Recovery

Если Draft уже был перемещен в Confirmed, но предыдущий запуск прервался до завершения pipeline, повторная обработка продолжает работу непосредственно из Confirmed.

Draft существует  
→ Draft перемещается в Confirmed  
→ batch обрабатывается  
  
Draft отсутствует, Confirmed существует  
→ обработка продолжается из Confirmed  
  
Archive существует  
→ idempotent success  
  
Batch отсутствует в Drafts, Confirmed и Archive  
→ реальная ошибка состояния; confirm callback сохраняется для retry

### 11.12 Итоговое уведомление и ACK

После обработки Apps Script создает Voice/Outbox/voice_notification\_{batch_id}.json.

Nodul проверяет, не существует ли notification_sent ACK; при отсутствии ACK отправляет сообщение в Telegram и только после успешной отправки создает {batch_id}\_notification_sent.json.

Apps Script валидирует ACK, проверяет batch_id, удаляет соответствующий Outbox-файл и после успешной обработки удаляет ACK callback.

Если Outbox-файл уже отсутствует, повторный ACK считается idempotent success. Такой протокол обеспечивает single-delivery semantics для итогового уведомления.

### 11.13 Совместимость с Voice Transaction Batch Schema v1.0

Apps Script временно принимает schema_version 1.0 и 2.0. Это является parser compatibility, а не сохранением старой семантики v1.0.

Legacy-поля intent, target_hint, owner, operation_id, confidence_score и warnings могут присутствовать в старом batch, но не являются источником истины и не должны влиять на запись.

update_planned и fuzzy matching больше не являются поддерживаемым voice behavior.

### 11.14 Полная спецификация

Полная нормативная спецификация приведена в отдельном документе: Voice Transaction Batch Schema v2.0.

### 12.3 Жизненный цикл Voice batch

1\. Telegram передает голосовое сообщение в Nodul.

2\. Nodul выполняет STT.

3\. Nodul читает voice_ner_prompt.txt и передает LLM CURRENT_DATE и TRANSCRIPT.

4\. LLM возвращает только operations\[{date, amount, type, comment}\].

5\. Если валидных операций нет, Draft не создается и пользователь получает recognition error.

6\. Если операций больше пяти, batch отклоняется целиком.

7\. Nodul собирает Voice Transaction Batch v2.0.

8\. Nodul сохраняет {batch_id}.json в Voice/Drafts/.

9\. Nodul отправляет confirmation card в Telegram.

10\. Пользователь нажимает "✅ Подтвердить".

11\. Nodul создает Voice/Callbacks/{batch_id}\_confirm.json.

12\. Apps Script обрабатывает confirm.

13\. При наличии Draft он перемещается в Confirmed.

14\. Apps Script выполняет normalize / owner / operation_id / validate / idempotency.

15\. Валидные новые операции записываются в лист "Календарь".

16\. После успешной обработки batch перемещается в Archive.

17\. Apps Script создает Voice/Outbox/voice_notification\_{batch_id}.json.

18\. Nodul проверяет наличие notification_sent ACK.

19\. При отсутствии ACK Nodul отправляет итоговое сообщение в Telegram.

20\. После успешной отправки Nodul создает Voice/Callbacks/{batch_id}\_notification_sent.json.

21\. Apps Script валидирует ACK и удаляет соответствующий Voice/Outbox-файл.

22\. После успешной обработки callback/ACK-файл отправляется в Trash.

### 12.4 Повторный confirm

Если пользователь повторно нажимает остающуюся в Telegram кнопку "✅ Подтвердить", Nodul может снова создать confirm signal.

Если batch уже находится в Archive, Apps Script считает повторный confirm idempotent success. Повторный confirm не приводит к повторной записи в "Календарь", повторному итоговому уведомлению или ошибке отсутствующего Draft.

### 12.5 Отмена

Cancel signal не используется в Voice Transaction Batch Schema v2.0. Удаление Telegram inline keyboard после подтверждения также не является частью runtime. Безопасность повторного нажатия обеспечивается идемпотентностью, а не изменением Telegram message markup.

## 13. Обновление листа "Календарь"

### 13.1 Назначение

Лист "Календарь" является источником зарегистрированных финансовых операций проекта. Voice pipeline v2.0 создает только новые фактические операции.

### 13.2 voice_operation_id

Для операций, созданных через голосовой ввод, используется поле voice_operation_id типа string в формате {telegram_message_id}\_{index}. Пример: 12345_0.

1\. Поле заполняется только для операций, созданных voice pipeline.

2\. Для обычных ручных операций поле остается пустым, если иное не требуется.

3\. Apps Script использует поле для operation-level idempotency.

### 13.3 Обязательные заголовки для VoiceInputManager

VoiceInputManager определяет необходимые колонки по именам заголовков, а не по их физическим номерам.

date  
owner  
actual_value_RUR  
type  
comment  
voice_operation_id

Физический порядок этих колонок не является частью voice-контракта.

### 13.4 plan_value_RUR

Лист "Календарь" может содержать plan_value_RUR как часть основной модели бюджета. Однако voice pipeline не требует plan_value_RUR, не выполняет поиск плановой операции, не изменяет plan_value_RUR, не обновляет существующую плановую строку и не выполняет fuzzy matching.

Каждая подтвержденная voice operation создается как отдельная фактическая операция.

### 13.5 Знаковая конвенция

В Voice Transaction Batch amount хранится как положительная величина. При записи в actual_value_RUR Apps Script применяет знак: Расход → отрицательное число; Доход → положительное число.

### 13.6 Обратная совместимость

Существующие плановые и ручные строки "Календаря" не требуют миграции. Добавление и использование voice_operation_id не должно менять смысл существующих финансовых данных. VoiceInputManager должен адаптироваться к физическому расположению колонок через поиск по заголовкам.

VoiceInputManager.gs является Apps Script-модулем нормализации, валидации, идемпотентной регистрации и lifecycle-обработки подтвержденных голосовых операций.

Ответственность VoiceInputManager.gs:

1\. Обработка confirm callback-файлов.

2\. Перемещение batch Drafts → Confirmed.

3\. Продолжение обработки batch, уже находящегося в Confirmed.

4\. Определение batch state: Draft / Confirmed / Archive.

5\. Нормализация Voice Transaction Batch.

6\. Определение owner по telegram_user_id.

7\. Генерация operation_id в формате {telegram_message_id}\_{index}.

8\. Валидация schema_version, даты, суммы, owner, type, comment и количества операций.

9\. Проверка operation-level idempotency через voice_operation_id.

10\. Обработка repeat-confirm как batch-level idempotency.

11\. Запись новых фактических операций в лист "Календарь".

12\. Best-effort rollback при ошибке пакетной записи.

13\. Перемещение успешно обработанного batch в Voice/Archive.

14\. Создание одного итогового уведомления в Voice/Outbox.

15\. Обработка notification_sent ACK.

16\. Удаление соответствующего Outbox-файла только после валидного ACK.

17\. Housekeeping неподтвержденных Draft.

18\. Диагностика и безопасные технические тесты.

VoiceInputManager.gs не отвечает за:

1\. получение Telegram webhook;

2\. скачивание аудио;

3\. STT;

4\. LLM NER;

5\. fuzzy matching;

6\. обновление плановых операций;

7\. confidence-based decision;

8\. удаление Telegram inline keyboard;

9\. прямые Telegram API HTTP-вызовы;

10\. финансовые расчеты.

Ключевые функции текущей реализации:

processVoiceCallbacks\_() — обработка confirm и notification_sent callback.

\_handleConfirmAction\_(batchId) — state-aware обработка подтверждения и repeat-confirm idempotency.

processConfirmedVoiceBatch(batchId) — normalize / validate / idempotency / Calendar / Archive.

processVoiceBatch\_(batch) — нормализация, валидация и разделение новых/дублирующихся операций.

writeOperationsToCalendar\_(operations) — запись новых фактических строк с rollback при ошибке.

\_handleNotificationSentAction\_(batchId, ackFile) — обработка delivery ACK и cleanup Outbox.

\_sendVoiceNotification\_(chatId, message, batchId) — создание итогового Voice/Outbox request.

### 16.5 Асинхронный pipeline

Apps Script поддерживает асинхронное выполнение pipeline с автоматическим ожиданием ответа от внешнего AI-оркестратора.

## 17. Работа с искусственным интеллектом

### 17.1 Роль искусственного интеллекта

В текущей версии проекта LLM используется в двух независимых режимах:

1\. Report Analysis / HTML — LLM анализирует подготовленные финансовые данные и формирует готовый HTML-документ текущего HTML-first pipeline.

2\. Voice NER — LLM извлекает минимальный набор структурированных сущностей из транскрипта голосового сообщения.

Эти режимы имеют разные prompts и разные runtime-контракты и не должны смешиваться.

### 17.2 Ответственность LLM в report pipeline

1\. анализ данных;

2\. выявление закономерностей;

3\. объяснение изменений;

4\. формирование выводов;

5\. оценку рисков;

6\. подготовку рекомендаций;

7\. генерацию готового HTML-документа.

Google Sheets остается владельцем финансовых показателей и расчетов.

### 17.3 Ответственность LLM в Voice NER

Voice LLM получает CURRENT_DATE, TRANSCRIPT и runtime instructions из voice_ner_prompt.txt.

LLM возвращает только:

{  
"operations": \[  
{  
"date": "DD.MM.YYYY",  
"amount": 1000,  
"type": "Расход",  
"comment": "..."  
}  
\]  
}

LLM Voice NER отвечает только за количество операций, date, amount, type и comment.

### 17.4 Ограничения Voice LLM

1\. не определять owner;

2\. не создавать operation_id;

3\. не определять intent;

4\. не искать плановую операцию;

5\. не выполнять fuzzy matching;

6\. не принимать решение update_planned;

7\. не принимать решение о записи в Google Sheets;

8\. не выполнять финансовые расчеты;

9\. не выбирать Расход или Доход только на основании наличия суммы.

Если направление денег нельзя определить однозначно, operation не создается. Если валидных операций нет или операций больше 5, возвращается {"operations":\[\]}. Частичный batch запрещен.

### 17.5 Независимость модели

Проект не зависит от конкретной языковой модели. Допускается использование разных LLM-провайдеров при условии соблюдения соответствующего runtime-контракта.

Для report pipeline обязательным является соблюдение действующего AI Job Package / HTML-first режима. Для Voice NER обязательным является соблюдение Voice Transaction Batch Schema v2.0 и актуального voice_ner_prompt.txt.

### 17.6 Хранение prompts

Report pipeline: текстовые инструкции текущего report pipeline хранятся в PromptTemplates.gs.

Voice NER: актуальный runtime prompt хранится отдельно в AI Workspace/Voice/Prompts/voice_ner_prompt.txt. Nodul должен читать этот файл перед LLM-вызовом.

Voice prompt не должен дублироваться как независимая live-копия внутри Nodul-кода или VoiceInputManager.gs.

### 17.7 Независимость от STT-провайдера

Voice Transaction Batch Schema не зависит от конкретного STT-провайдера. Допускается использование OpenAI Whisper, Yandex SpeechKit, Google Cloud STT, локальных моделей и других будущих провайдеров.

Замена STT-провайдера не должна менять Voice Transaction Batch Schema или ответственность Apps Script.

## 18. Работа с Google Drive

### 18.1 Роль DriveManager

DriveManager является единственным модулем, отвечающим за работу с Google Drive.

Он обеспечивает:

> 1\. создание структуры папок проекта;
>
> 2\. централизованный доступ к папкам;
>
> 3\. управление файлами в AI Workspace;
>
> 4\. архивирование готовых отчетов;
>

### 18.2 Принцип единой точки доступа

Все операции с Google Drive должны выполняться через DriveManager.

Запрещается прямое обращение к DriveApp из других модулей.

### 18.3 Разделение рабочих и архивных данных

AI Workspace содержит только актуальные файлы текущего отчета.

Reports содержит неизменяемые архивы всех завершенных отчетов.

Voice/Archive содержит архив всех обработанных голосовых батчей.

### 18.4 Принцип атомарности архивирования

Архивирование отчета выполняется только после успешного завершения всего конвейера.

Это обеспечивает целостность архива: каждая папка в Reports содержит полный комплект файлов.

### 18.5 Интеграция с внешним оркестратором (Nodul)

DriveManager обеспечивает структуру папок, совместимую с внешним оркестратором.

**Report pipeline:**

1\. Apps Script создает AI Job Package.txt в AI Workspace/Job/.

2\. Nodul отслеживает появление или изменение файла.

3\. Nodul читает AI Job Package.

4\. Nodul передает задание LLM.

5\. LLM возвращает HTML.

6\. Nodul сохраняет AI_Report.html в AI Workspace.

7\. Apps Script импортирует результат и завершает pipeline.

**Voice pipeline:**

1\. Nodul принимает Telegram update.

2\. Nodul проверяет авторизацию пользователя.

3\. Для voice message Nodul загружает аудио.

4\. Nodul отправляет аудио в STT.

5\. Nodul получает TRANSCRIPT.

6\. Nodul читает AI Workspace/Voice/Prompts/voice_ner_prompt.txt.

7\. Nodul декодирует содержимое prompt в UTF-8.

8\. Nodul добавляет CURRENT_DATE и TRANSCRIPT.

9\. Nodul вызывает LLM Voice NER.

10\. LLM возвращает operations\[{date, amount, type, comment}\].

11\. Nodul валидирует структуру результата.

12\. При отсутствии валидных операций Nodul отправляет recognition error и не создает Draft.

13\. Nodul собирает Voice Transaction Batch v2.0.

14\. Nodul сохраняет batch в Voice/Drafts/.

15\. Nodul отправляет confirmation card в Telegram.

16\. Пользователь нажимает "✅ Подтвердить".

17\. Nodul создает {batch_id}\_confirm.json в Voice/Callbacks/.

18\. Apps Script обрабатывает batch: Drafts → Confirmed → normalize / validate / idempotency → Calendar → Archive.

19\. Apps Script создает voice_notification\_{batch_id}.json в Voice/Outbox/.

**Voice notification delivery:**

1\. Nodul отслеживает Voice/Outbox.

2\. До отправки Nodul проверяет наличие notification_sent ACK.

3\. Если ACK уже существует, повторное сообщение не отправляется.

4\. Если ACK отсутствует, Nodul отправляет итоговое сообщение пользователю.

5\. После успешной Telegram-доставки Nodul создает {batch_id}\_notification_sent.json в Voice/Callbacks/.

6\. Apps Script валидирует ACK.

7\. Apps Script удаляет соответствующий Voice/Outbox-файл.

8\. После успешной обработки ACK callback удаляется.

Nodul не удаляет созданный Apps Script Outbox-файл напрямую.

Cancel callback и удаление inline keyboard не являются частью live Voice v2.0.

**Результат**

После подтверждения Apps Script детерминированно определяет owner и operation_id, валидирует batch и записывает операции в Google Sheets.

Повторное нажатие кнопки подтверждения не создает вторую запись и не приводит к повторному итоговому уведомлению.

Если LLM не может надежно определить обязательные данные операции, система предпочитает отказ от записи предположению.

## Приложение C. Три сценария Nodul

В проекте используются три независимых сценария Nodul:

| **№** | **Сценарий**           | **Триггер**                                          | **Назначение**                               |
|-------|------------------------|------------------------------------------------------|----------------------------------------------|
| 1     | AI Pipeline            | AI Workspace/Job/AI Job Package.txt                  | Отправка задания в LLM, получение HTML       |
| 2     | Telegram Report Sender | AI Workspace/Telegram/Outbox/telegram_request.json   | Отправка HTML-отчета в Telegram              |
| 3     | **Voice Input**        | **Telegram webhook (message.voice, callback_query)** | **Распознавание голоса, NER, подтверждение** |

Все сценарии используют одинаковый архитектурный подход:

> 1\. Файловый контракт (request → response).
>
> 2\. Изоляция от Apps Script.
>
> 3\. Независимость от конкретных технологий.
