## Фактическая проверка

В постоянной приватной QA-папке обнаружен один результат Development v42. Результат прочитан по фактическому Drive ID. Связанная заявка прочитана по `request_file_id` результата. Подтверждены непосредственная QA-папка, UUID, report_id, request_id, попытка 1 из 4, ID и имя кандидата, SHA-256 скачанных байтов. Все пять ширин (320, 375, 390, 430 и 768 px) прошли геометрию без замечаний. Результат относится к копии HTML и копии заявки, обработанным v42. SHA-256 HTML совпал с зафиксированным на START, SHA-256 test-копии выгрузки совпал с закреплённым в инструкции START.

Штатный `check_numbers.py --html` из закреплённой ревизии BUILD повторил 188 проверок с нулём нарушений. История START и QA-заявка фиксируют три успешные проверки анализа. Инструкция START создаёт `analysis_N.json` во временной рабочей папке и сохраняет в Drive HTML и QA-заявку. В приватной папке пилота и QA оригинал анализа не обнаружен. Заменять его сгенерированным заново текстом или извлечённым из HTML фрагментом для этой проверки нельзя.

Сохранена приватная резервная копия текущей инструкции Event Intake, её содержимое сверено после скачивания. Действующая инструкция и триггер не обновлялись. Outlook-событие не отправлялось. Новый браузерный прогон, QA-заявка и тестовый финал не создавались.

## Подготовленная ветка VALIDATED

1. Прочитать входящее Gmail-письмо по ID события и применить действующую общую проверку From и темы. Принять только маркер `FBA_EVENT_V2` и точные поля `event`, `run_id`, `report_id`, `event_id`, `validation_file_id` без дубликатов. Маршрутизировать сюда только `VALIDATED` для разрешённого запуска из приватной конфигурации. При несоответствии для этого запуска остановиться. Сохранить прежнюю диспетчеризацию START, REPAIR, EXCEPTION и других VALIDATED.
2. Из приватной конфигурации получить разрешённые папки QA, исходных файлов и тестового финала, закреплённую ревизию BUILD, ожидаемые идентификаторы и хеши входов, включая оригинальный анализ. Привязать разрешённое событие к конкретной проверенной заявке, версии контракта и SHA-256 кандидата. Проверить event_id по согласованному формату транспорта. При отсутствии оригинала анализа завершить с `VALIDATED_REJECTED / ANALYSIS_ARTIFACT_MISSING`.
3. Прочитать результат по `validation_file_id` из письма и заявку по `request_file_id` из результата. Проверить фактические метаданные активных файлов, непосредственного родителя, ожидаемые точные имена, отсутствие ярлыков, роли и MIME. Принять наблюдаемый `text/plain` для JSON-результата v42 после строгого разбора JSON. Отклонить дубликаты ключей, несогласованную схему v2.0, идентификаторы, номер попытки, лимит попыток, статусы и SHA-256. Проверить идентичность числовых подтверждений заявки и результата. Требовать пять уникальных заданных ширин, `passed=true`, отсутствие переполнений и замечаний.
4. Скачать кандидата по подтверждённому ID, проверить единственного непосредственного родителя и SHA-256 полных байтов. Скачать закреплённую выгрузку и оригинальный анализ, сверить ID, родителя и SHA-256, проверить схему и номер отчёта выгрузки. Запустить независимые `check_numbers.py --text` и `check_numbers.py --html` на скачанных файлах. Для обеих команд требовать код 0, `ok=true`, положительное целочисленное число проверок и пустой список нарушений. Сверить счётчики с заявкой. Остановиться при любой неопределённости.
5. Непосредственно перед записью перечислить все страницы активных прямых потомков разрешённой тестовой папки. При точном совпадении имени `test_final_{run_id}_aNN.html` закончить без записи с диагностикой существующего финала. Загрузить один файл как `text/html`, используя проверенные байты без конвертации. Проверить фактические имя, ID, MIME и родителя, повторно скачать и сверить SHA-256. При неопределённом результате или расхождении остановиться без повторной записи. Только после подтверждения вернуть `VALIDATED_PUBLISHED_TEST`. Контроль наличия файла защищает от последовательных дублей. Одновременная обработка писем остаётся за рамками теста.
