4. Скачать кандидата по подтверждённому ID, проверить единственного непосредственного родителя и SHA-256 полных байтов. Скачать закреплённую выгрузку и оригинальный анализ, сверить ID, родителя и SHA-256, проверить схему и номер отчёта выгрузки. 5. Непосредственно перед записью перечислить все страницы активных прямых потомков разрешённой тестовой папки. При точном совпадении имени `test_final_{run_id}_aNN.html` закончить без записи с диагностикой существующего финала. Загрузить один файл как `text/html`, используя проверенные байты без конвертации. Только после подтверждения вернуть `VALIDATED_PUBLISHED_TEST`. Контроль наличия файла защищает от последовательных дублей. Одновременная обработка писем остаётся за рамками теста.

## Решение по блокеру анализа — исправление контракта BUILD

По исходной инструкции Work v0.1.0 `analysis_N.json` создавался только в эфемерной рабочей директории; долговременная запись оригинала не входила в контракт `START_BUILD_QA_READY`. Совпадение HTML с кандидатом и исторический счётчик трёх проверок анализа **не заменяют** повторную независимую сверку оригинала. Не дописывать к прежнему запуску верификацию на основе заново созданного анализа или извлечённого из HTML текста.

В черновом [PR №10](https://github.com/malderivan-berg/family-budget-automation/pull/10) инструкция `agent/report_agent_work.md` дополнена как **v0.1.1 (draft)**: перед созданием QA-заявки сохраняются исходный `analysis_{run_id}_a01.json` с побайтовой проверкой и `fba_build_evidence_{run_id}_a01.json` со ссылками, ID и SHA-256 выгрузки, оригинального анализа и кандидата. QA request остаётся **строго прежней схемы v2.0**, без новых полей и без изменения Nodul v42. Независимый запуск VALIDATED обязан прочитать оригинальный анализ и доказательство BUILD из заранее разрешённой приватной папки, сопоставить с QA-result и повторить оба запуска `check_numbers.py`.

**Статус:** исправлена только версионированная черновая инструкция GitHub; событийная задача Work пока не обновлена, реализация v0.1.1 не испытана. Для текущего run_id восстанавливать оригинал лишь из реально существующего файла/сохранённой рабочей среды с доказуемым происхождением; при отсутствии оригинала этот запуск оставить как `ANALYSIS_ARTIFACT_MISSING` и без тестового финала. Для следующего опыта потребуется отдельный новый UUID и новый START, затем сохранение четырёх BUILD-артефактов, независимый QA и одно разрешённое VALIDATED-событие. Не переиспользовать прежний результат Nodul для другого кандидата. До одобрения не отправлять Outlook и не расширять production.

## Контрольный BUILD v0.1.1 и однократное выполнение QA — 24.11.2026

Для нового ограниченного запуска по разрешённому START Work автоматически вернул `START_BUILD_QA_READY`: в доверенных Drive-папках сохранены исходный анализ, HTML-кандидат, отдельный `fba_build_evidence` и QA-заявка v2.0 (последняя в последовательности записи). После повторного чтения файлов по фактическим ID подтверждены связи и SHA-256. `check_numbers.py` проверил 3 числовых вхождения анализа и 188 HTML, нарушений 0. В этом запуске проблема `ANALYSIS_ARTIFACT_MISSING` **устранена фактически**, не только в инструкции.

Один `Run once` Nodul Development v42 в 19:06:46 МСК завершился «Успешно», но только с **1 операцией**; отсутствуют результат QA, запись `VALIDATED` и тестовый финал. Возможное объяснение — разовый Drive-триггер обнаружил создаваемый HTML раньше QA-заявки, после чего ребро входного фильтра не запустило дальнейший граф. **Это гипотеза:** точный file ID/имя события и решение фильтра в истории ещё не установлены. Не считать успешный статус Nodul доказательством QA.

Следующий шаг без нового START/BUILD: (1) прочитать сохранённый выход триггера №17 и проверить, был ли получен HTML либо QA JSON; (2) подтвердить отсутствие QA-result/receipt по новому `run_id`; (3) если граф не изменён и результат отсутствует, архивировать только исходную заявку вне наблюдаемой QA-папки, сохранить HTML/analysis/evidence неизменными; (4) предварительно запустить один `Run once` и подтвердить состояние ожидания, затем создать **одну** новую копию QA-заявки с идентичными проверенными байтами, первоначальным `run_id`, ссылкой на прежний неизменённый `candidate_file_id` и новым фактическим ID файла заявки; (5) проверить прохождение N01/N03/N04/N05, пять ширин, SHA-256 и полученный `request_file_id`. При уже существующем результате, частичном состоянии либо отсутствии новых событий остановиться для диагностики, без повторных загрузок. Этот ручной повтор не равен подтверждению полностью автоматической доставки READY_FOR_LAYOUT в Nodul.

Outlook остаётся `0 = 1`, Active выключен, Prod не развёрнут. `VALIDATED`-письмо и `test_final` до успешной QA и отдельного разрешения на отправку не создавать. Никаких изменений GAS, Sheets, Stable Pilot и Telegram.
