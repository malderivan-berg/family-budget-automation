# Подготовка тестового GAS и Event Intake для №22

Тестовый модуль — [FbaWorkE2e.js](../tests/e2e/fba22/FbaWorkE2e.js). Файл хранится вне production apps-script и не включается в штатный clasp push.

## Изолированный Apps Script

1. В тестовой копии Sheets открыть Расширения → Apps Script. Сверить Spreadsheet ID, отдельный Script ID и отсутствие установленных триггеров. Оставить для стенда только функции, необходимые для createNewReport_ и exportReportData_, и их зависимости. Не запускать функции Main, Claude, Voice или штатного Telegram. Добавить модуль FbaWorkE2e и сервис Google Drive API v3.
2. В Script Properties тестового проекта добавить FBA22_CONFIG как JSON. Поля: testSpreadsheetId, productionSpreadsheetId, testRootFolderId, startFolderId, runFolderId, finalFolderId, outboxFolderId, inboxFolderId, userId, chatId, reportMinutes, deliveryMinutes. Пять рабочих папок должны быть прямыми потомками testRootFolderId. userId и chatId взять из проверенной конфигурации единственного получателя «Муж». Использовать строки. Токены этому модулю не нужны.
3. Запустить testFba22DeliveryEvidence и проверить FBA22_ACK_TEST_OK. Выполнить prepareFba22Run один раз. Функция создаёт новый расчётный блок и выгрузку в тестовом контуре, закрепляет reportId, runId, dataId, dataSha256 и резервирует startId без публикации START. Прочитать эти поля из FBA22_STATE только в приватной конфигурации стенда. При остановке на PREPARING проверить частично созданные артефакты вручную, без запуска нового отчёта.
4. После полного подтверждения изоляции Relay, QA и Sender и установки правила Event Intake запустить startFba22Run один раз. GAS перечитывает выгрузку, создаёт контрольный триггер и публикует START с зарезервированным ID. Зафиксировать факт появления единственного START и время. При неопределённом результате сначала проверить резервированный ID и историю Relay, сохраняя исходный UUID.
5. При откате остановить триггер функцией stopFba22DeliveryCheck и оставить FBA22_STATE и артефакты для расследования. Поставить на паузу только тестовые сценарии Nodul и удалить добавленный блок №22 из Event Intake. Возврат состояния после возможной отправки Telegram не разрешает новую отправку.

## Ручное обновление существующей событийной задачи

Текущая автоматизация найдена по ID. Интерфейс чтения возвращает текст инструкции, но не выдаёт полный существующий набор триггеров. Для изменения через интерфейс владельца открыть связанный чат, открыть настройки именно FBA — Agent v2 Event Intake и сохранить точную резервную копию текущей инструкции приватно. После подготовки GAS добавить перед первой веткой №20 блок ниже, заполнив поля фактическими данными только внутри Task. В редакторе оставить прежними Gmail-триггер, From, тему и статус. После сохранения повторно открыть задачу и сверить эти поля и наличие прежних веток. Если редактор не позволяет сохранить полную инструкцию с добавлением, остановиться до START.

> ### Приоритетный маршрут №22 — один запуск
>
> 1. Прочитай письмо по Gmail ID webhook. Проверь INBOX, точные технические From и тему по текущей задаче, уникальный маркер FBA_EVENT_V2, ровно пять уникальных полей и корректные типы. Если run_id не совпадает с [RUN_ID_22], выполни исходную диспетчеризацию. Для совпавшего run_id разреши только START и VALIDATED с report_id=[REPORT_ID_22]. При другом событии или ошибке заверши ветку без записей.
> 2. START. Выполни [версию и commit SHA инструкции агента Work] с закреплёнными [START_ID], [START_OUTBOX_ID], [RUN_FOLDER_ID], [QA_FOLDER_ID], [DATA_ID], [DATA_SHA256], [FINAL_FOLDER_ID], [TELEGRAM_OUTBOX_ID]. В конфигурации этой ветки Telegram Outbox является ожидаемым полем манифеста; права записи в него предоставляются инструкции только на этапе VALIDATED. Сверь event_id по формуле START, схему, отчёт, непосредственных родителей, MIME, имена и полные байты. Сохрани анализ, кандидата и BUILD evidence, подтверди readback и числовые проверки. Создай QA request последним.
> 3. VALIDATED. В [QA_FOLDER_ID] найди по точному имени ровно один активный результат своей попытки, сопоставь его ID с validation_file_id и прочитай связанную заявку по request_file_id. Проверь имена, единственных непосредственных родителей, MIME, схемы, UUID, report_id, request_id, попытку, PASS_GEOMETRY на 320/375/390/430/768 и формулу event_id. По BUILD evidence из [RUN_FOLDER_ID] проверь связи ID и SHA-256 выгрузки, оригинального анализа и кандидата. Повтори обе числовые проверки по закреплённой ревизии и требуй положительные счётчики и нулевые нарушения. При ошибке запрети публикацию.
> 4. Создай в [FINAL_FOLDER_ID] единственный report_N.html из проверенных байтов. Повторно скачай по ID и проверь SHA-256 кандидата, имя, MIME и родителя. Перед первой записью перечисли прямых потомков с пагинацией. Любое ранее существующее или частичное состояние оставь для проверки, без повторной записи. После подтверждения финала и проверки отсутствия запроса запиши один Telegram Request v1.1 с MIME text/plain в [TELEGRAM_OUTBOX_ID], только для проверенных [USER_ID_22] и [CHAT_ID_22]. Не используй delivery.users из выгрузки. Соблюдай поля и имена действующего Handbook. Не вызывай Telegram сам. На повторном письме при существующих артефактах не создавай новый Request. Соблюдай запрет параллельной обработки одного run_id.
> 5. Сообщи статусы этапов и числовые счётчики без финансового содержимого, адресов и приватных ID.

Все значения в квадратных скобках должны быть заполнены и проверены до сохранения. Штатный Sender не должен наблюдать тестовый Telegram Outbox.
