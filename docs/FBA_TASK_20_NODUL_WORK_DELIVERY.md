## Продолжение: задача №21 — диагностика N02a и идемпотентности (частично выполнена)

**Источник:** [протокол задачи №21 в комментарии PR №13](https://github.com/malderivan-berg/family-budget-automation/pull/13#issuecomment-7157920770). Development v44 не менялся, Active Off, Prod не развёрнут, Outlook заблокирован. Указанные ниже `SKIP` и `RESEND` являются результатами **изолированного исполнения кода**, а не подтверждёнными ветками сценария Nodul.

- Сохранённая история повторного `Run once` 25.11.2026 11:42:29 МСК: обе итерации N02a (№24) успешно получили содержимое №23, вернули поля `text` и `bytes=1877`. Ребро 24 → 4 присутствует, условие пустое, Fallback выключен, N02 (№4) — Bun. N02 не выполнялся; причина остановки и механизм доставки пакетов **не установлены**.
- В изолированном тесте N02: при согласованном результате и существующей квитанции код возвращает `SKIP`; при том же результате без квитанции — `RESEND` с исходным JSON. Puppeteer, Outlook, запись в Drive и runtime-маршруты не запускались.
- **Пробел идентичности:** логические `request_id` (включая `run_id`) и SHA-256 кандидата недостаточны: при замене фактических Drive ID заявки и кандидата код по-прежнему возвращает `SKIP`. Признак квитанции определяется существованием файла с именем, без разбора содержимого. Повтор задачи №20 использовал копию заявки с новым Drive ID, то есть не был точным повтором исходного Drive-события.
- **Минимальная коррекция контракта (предложение, не внедрено):** перед `SKIP/RESEND` проверять оригинальный `request_file_id` из сохранённого QA-result на совпадение с фактически обрабатываемой заявкой; проверять `candidate_file_id` с ID кандидата по доверенной исходной заявке и метаданным Drive, а при наличии идентификатора кандидата в QA-result — и с ним. Не добавлять обязательные поля в QA schema v2.0 без отдельной версии. Одноимённую квитанцию принимать только после проверки `event_id`, `request_id`, `validation_file_id`; несовпадения, несколько файлов и неопределённое состояние должны давать явный отказ, а не `SKIP`. Для заявки-копии с новым ID использовать fail-closed до отдельного решения о семантике повторов.
- **RESEND:** отсутствие квитанции после создания результата не доказывает отсутствие отправленного Outlook-письма. Перед реальной переотправкой сверять почтовую историю по точному `event_id` и следы запуска; при неопределённости останавливать сценарий и требовать ручной разбор. Проверка Work на повторно доставленном письме отдельно не выполнялась.
- **Происхождение BUILD:** Work для выделенного QA-пилота №20 явно закреплял допустимую связь с BUILD №19 (точные ID/SHA-256/ревизия). Это проверка конфигурации, а не отрицательный runtime-тест на подмену источника. В production нельзя считать SHA-256 HTML единственным доказательством права использовать артефакты другого `run_id`.

**Следующий тест:** сначала исследовать формат выхода N02a, входные маппинги и runtime-маршрут 24 → 4 без изменений боевого контура. Затем в изолированной Development-копии подтвердить штатный `SKIP` на **том же** `request_file_id` и `RESEND` при корректном result без receipt с запретом Outlook. Отдельно прогнать отрицательные случаи с другим Drive ID и одноимённой неверной квитанцией. Запись/отправку, Deploy/Active и любые изменения production не выполнять без отдельного разрешения.

В успешной ветке v43 до появления результата Map-флаги были `"false"`, JSON пуст, N02 вернул `VALIDATE`. Номер исходной итерации №24, выбранной одиночным запуском, интерфейс не показал. **Одиночный N02 подтверждает вычислимость привязок для использованного набора, но не передачу двух пакетов по ребру 24→4.** `SKIP` выдан старой версией N02 на данных копии заявки с другим Drive ID: его нельзя интерпретировать как приёмку исправленной идемпотентности.

Сначала один элемент, затем два; сравнить число выходных элементов B с числом фактических запусков C и проверить, какую итерацию видит C. Потом проверить тот же путь с условной Map-подстановкой и с прямым маршрутом в обход B. Не добавлять стенд в v44, не использовать Drive/Outlook/Gmail/Telegram и не запускать полную QA. При воспроизведении сбоя отправить подготовленное обезличенное обращение в поддержку **только после согласования отправки**; если стенд проходит, локализовать различие конфигурации реального графа (слияние веток/итераций/входные Map). До подтверждения маршрута исправленный модуль N02 остаётся только в GitHub.

## Задача №21 — стенд A → B → C: три успешных прогона

25.11.2026, 13:07–13:12 МСК. В полностью отдельном сценарии Nodul (ручной триггер №1, Итератор A №2, Bun B №3 и C №4) подтверждён проход одного и двух синтетических пакетов через B→C. Ни один тест не подключался к Google Drive, Outlook, Gmail, Telegram или production.

| Версия | Вход | Операции B/C | Результат | Ограничение |
| --- | --- | --- | --- | --- |
| v5 | 1 элемент | 1/1 | C получил `item-1`, `executed=true` | Линейный маршрут |
| v6 | 2 элемента | 2/2 | C получил оба элемента, `executed=true` | Линейный маршрут |

Строковые `element`, `text`, `bytes` корректно поступили в C; ошибок исполнения не зафиксировано. **Передача одного/двух элементов и наличие условного ребра сами по себе не воспроизводят остановку v44.** Историческая остановка N02a №24 → N02 №4 остаётся без установленной причины. v44 строит N02 input из нескольких источников: `$3`, `$24.text`, `$30.result` и `$31.result`; две независимые проверки присутствия выполняются с `length(map(...))` по спискам. Стенд проверял иное: один Iterator cycle и скалярную условную подстановку.

**Следующий ограниченный опыт:** расширить только синтетический стенд до двух отдельных источников массивов с полями `id`, `name`, `element`. Перед C вычислять именно два выражения `length(map(...))`, соответствующие N02 (а не заменять их упрощённой проверкой). Сравнить: 1 пакет с отсутствующей квитанцией, 2 пакета с результатом и квитанцией, затем вариант с неодинаковыми числами элементов в двух списках. В каждой ветке фиксировать значения и типы обоих флагов, значения `$B.text`, количество операций C, ошибки параметров и соответствие пакета конкретному `element`. В отдельном контрольном опыте заменить только один `map` на заранее вычисленный скаляр; сравнить поведение. Это **диагностические проверки**, не правила для production.

Если расширенный стенд воспроизводит остановку, изолировать конкретное выражение или рассинхронизацию элементов и использовать эту воспроизводимость в обращении к поддержке Nodul. Если нет — ограничиться read-only сопоставлением real v44 с работающим стендом, особенно источниками/итерациями и входными привязками №4. До установления причины не перестраивать Dev v44 и не внедрять строгий N02. Контракт QA v2.0, Active Off, Outlook `0 = 1`, без Deploy и письма — без изменений.
