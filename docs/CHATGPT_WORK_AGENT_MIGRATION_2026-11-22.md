# Миграция агента отчёта: Claude → ChatGPT Work

| Поле | Значение |
|---|---|
| Дата решения | 2026-11-21 (подтверждено 2026-11-22) |
| Статус | **Целевая архитектура / Proposed migration**: замена агента согласована, production ещё не переключён |
| Причина | Claude недоступен пользователю; роль агента финансового отчёта берёт на себя ChatGPT Work |
| Прототип | Отчёт №10, полный цикл ChatGPT Work ↔ Drive ↔ Nodul ↔ Outlook/Gmail |
| Приоритеты | Надёжность → Простота → Масштабируемость → Автоматизация |
| Прежний аудит | [Аудит от 22.11.2026](PILOT_TO_PRODUCTION_QA_AUDIT_2026-11-22.md) **отменён**: ошибочно предполагал продолжение использования Claude |

## 1. Что решено

**ChatGPT Work — целевой исполнитель роли агента отчёта вместо Claude.** Он должен читать выгрузку, выполнять анализ/создание HTML и проверки из текущего GitHub-репозитория, работать через инструменты/подключённые сервисы в рамках ограниченных прав, обрабатывать события `START`, `REPAIR`, `VALIDATED`, `EXCEPTION`. Только Google Sheets остаётся источником финансовых показателей и расчётов.

Никакого возврата к Claude, переноса основной браузерной проверки из Nodul в `render_check.py` ради поддержки Claude или отказа от подтверждённого цикла Work ↔ Nodul не планируется.

Текущий **Handbook v1.0 остаётся описанием развернутой ранее системы**, пока не завершена миграция. Текущий код GAS /fire и `agent/report_agent.md` обслуживает прежний вариант; нельзя считать, что он уже автоматически запускает ChatGPT Work.

## 2. Целевой поток

```text
Google Sheets (данные и расчёты)
   ↓
Apps Script (создание отчёта, report_data_N.json, запуск/контроль)
   ↓
START event (подтверждённый транспорт до ChatGPT Work; способ запуска из GAS ещё проектируется)
   ↓
ChatGPT Work — агент отчёта:
  - только экспорт Sheets как источник цифр
  - анализ, HTML, проверка всех чисел и SHA256
  - кандидат report_N_work_candidate_vNN.html + запрос QA в Drive
   ↓
Nodul Browser Validator (независимая проверка HTML)
  - проверка SHA256 и геометрии 320/375/390/430/768
  - VALIDATED / REPAIR / EXCEPTION через Drive + Outlook → Gmail
   ↓
ChatGPT Work (событие)
  - REPAIR: исправить HTML, повторить QA (ограниченные попытки)
  - VALIDATED: опубликовать финальный HTML
   ↓
Telegram Request в Outbox (последним)
   ↓
Nodul Telegram Sender (существующий сценарий 2)
   ↓
Telegram Response → Apps Script: контроль доставки
```

Разделение ответственности: Nodul валидирует геометрию, но не выполняет финансовые расчёты, не правит HTML и не определяет результаты анализа; Work не пишет в Sheets, не отправляет Telegram напрямую, не выдумывает числа. Work может использовать версии скриптов `agent/tools/` из одной фиксированной ревизии GitHub.

## 3. Что реально доказано на отчёте №10

- ChatGPT Work с подключённым Drive сформировал анализ и кандидаты HTML, сверил числа; после исправлений выдал валидированный финальный HTML.
- Nodul Browser Validator (20 функциональных узлов, 21 связь) проверил HTML и вернул `REPAIR`, затем `VALIDATED`; мобильная геометрия прошла на пяти ширинах.
- Письмо с техническими метаданными прошло Outlook → Gmail; Work обработал разные события в отдельных запусках; исходные финансовые данные из письма не принимались за источник истины.
- После восстановления t10 отдельно подтвердили N03, N04, N02 `SKIP`; `RESEND` после восстановления изучен только по коду.
- Экспорт Stable Pilot JSON получен, структурно проверен, должен храниться приватно.

Это подтверждает **концепцию** event-driven Work + Nodul на фиксированном отчёте №10, **но не промышленную готовность**: start/delivery/callback для произвольных N, права, мониторинг и ошибка/повторное событие требуют отдельной адаптации и испытаний.

## 4. Что можно оставить без изменений

| Компонент | Решение |
|---|---|
| Sheets и финансовые формулы | Без изменений |
| Контракт `report_data` schema 1.0/2.0 | Не переписывать, сохранить совместимость |
| GAS создание отчёта и выгрузка | Сохранить, адаптировать только запуск агента/контроль при необходимости |
| `agent/tools/show_data.py`, `render_report.py`, `check_numbers.py` | Использовать как единственный версионированный код построения/сверки |
| Финальная доставка `Telegram Request/Response`, Nodul Sender | Сохранить контракт и сценарий 2 |
| Nodul Browser Validator Stable Pilot | Использовать как эталон, **не перезаписывать рабочий пилот** |
| Правила секретов | Script Properties / Nodul credentials only; не в коде/промптах |

## 5. Какие изменения действительно необходимы

1. **Обобщение протокола (L3):** убрать жёсткую зависимость от `report_id=10`, папки отчёта №10, `FBA_R10_A01..A04`, имени пилотных файлов, фиксированного адресата, имени темы и ID тестового отчёта. При этом сохранить строгое ограничение конкретной отчётной папки, проверку SHA256, номер попытки, запрет дублирования и fail-closed.
2. **Стартовый транспорт (L3):** GAS ранее вызывает Claude `POST /fire` четырьмя полями; для ChatGPT Work нужно выбрать и подтвердить реальный поддерживаемый способ запуска из GAS через событие/посредник. Пилот доказал Gmail-триггер Work, но не доказал готового прямого API-триггера ChatGPT Work. Нельзя просто заменить URL без проверки.
3. **Агентская инструкция (L3 по процессу):** отдельная версионированная инструкция для ChatGPT Work, учитывающая данные `report_data`, публикацию только после `VALIDATED`, ограничение retries, проверку имён/папок/хешей, `Telegram Request` последним и сохранение существующих контрактов.
4. **Связка с действующей доставкой (L2/L3):** после `VALIDATED` создавать `report_N.html` и `telegram_request_N.json` в рабочем Outbox; проверять, что Nodul Sender и GAS видят те же форматы. Пока финал отчёта №10 записывался только в пилотную папку.
5. **Мониторинг и идемпотентность (L2/L3):** GAS 30-минутная проверка доставки, защита при повторных Gmail-событиях и неполных Drive-артефактах, аварийное уведомление. Проверить допустимое время многократного QA относительно таймера.
6. **Разделение Test/Production (L2):** изолированный прогон следующего отчёта с тестовой папкой и единственным тестовым получателем; сохранить текущую production-цепочку до успешного end-to-end и отдельного решения пользователя.

Классификация L3 оправдана изменением действующего официального интерфейса запуска Report Agent Fire Payload и введением event-driven QA-контракта. Основополагающий принцип «Sheets owns numbers» не меняется; L4 не требуется, если сохраняются роли компонентов и границы доступа.

## 6. Ближайший шаг (никаких запусков)

**P0 — спецификация универсального event-протокола и запуска ChatGPT Work.** Черновик спецификации создан: [FBA Work Event Protocol v0.1](WORK_EVENT_PROTOCOL_v0.1.md). Gmail-канал — основной, поскольку доказан на пилоте; прямой Workspace Agents API не считаем доступным без отдельного подтверждения. На основании фактической схемы пилотного запроса/результата/квитанции и текущих контрактов GAS/Telegram:
- определить стабильный уникальный ключ `report_id + run_id + attempt` для разных отчётов, исключив конфликт `FBA_R10_A01..A04`;
- выбрать поддерживаемый транспорт `GAS → ChatGPT Work START` с минимальными промежуточными компонентами и проверить документально/в тестовом событии (не обещать неподтверждённый API);
- определить `REPAIR`, `VALIDATED`, `EXCEPTION`, дедупликацию, таймауты, восстановление по Drive и права;
- составить таблицу минимальных изменений Nodul, инструкции агента и GAS без внедрения;
- отдельно проверить работу с существующим `Telegram Request/Response`.

Только затем, с явным разрешением пользователя, менять отдельные компоненты и запускать тест. **Никаких Deploy, Active, записи в рабочие Sheets, отправки реальных отчётов или изменения production на этапе спецификации.**

## 7. Отмена ошибочного маршрута

Предложение из аудита QA от 22.11.2026 «проверить Playwright/Chromium в Claude, усилить render_check.py и не переносить Outlook/Gmail/Work» **отменено**: оно противоречит решению заменить Claude на ChatGPT Work. Сведения того аудита о текущем `render_check.py` остаются историческим наблюдением, но его целевое решение и Roadmap-пункты недействительны.
